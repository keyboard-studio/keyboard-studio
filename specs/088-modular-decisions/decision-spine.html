keyboard-studio · spec 088 proposal · km/modular-decisions

One answer, one record, one write

Today a single answer is saved in up to four places and reaches the keyboard by one of three routes. The target has one source of truth: decisions. The keyboard is not saved at all. It is derived from the starting point and the decisions, and rebuilt whenever one of them changes.

keyboard = replay( starting point, apply(d1), apply(d2), … apply(dn) )   // decisions in dependency order

02 · The record

What a decision has to remember

Recalculation depends on knowing who chose each value. A value the author typed is kept when its inputs change. A value the studio supplied gets recomputed.

// decisionStore, saved in the draft per decision id "copyright-holder": { value: "Fatou Ndiaye", provenance: "default", source: "author-name", // what supplied it inputs: { "authoring-track": "copy" }, // requires, as seen offered: "SIL International", // extracted, shown beside it step: "identity" // display only }
asked

The author typed, picked or confirmed it. It is kept when its inputs change. It is re-proposed only if it no longer fits.

extracted

Read from the starting point by the module's extract, and labelled "from <keyboard>". It is re-extracted when the starting point or an input changes.

default

Supplied by a rule or a lookup such as langtags or the GitHub profile. It is recomputed.

derivednew

Computed from other decisions, such as carve proposals, suggested touch keys or generated help. It is recomputed. This would be a fourth provenance value, added in packages/studio only.

mixed

A collection where some items are hand-set and the rest are suggested, as with carve removals or touch keys. Each item carries its own provenance, as touch keys already do (spec 014).

05 · Rebuilding the keyboard

Replay from the first changed decision

If every apply returns a patch, the working copy is a pure function of the starting point and the records. Keep a checkpoint of the IR after each decision. A change then replays only from its own checkpoint forward, and the earlier checkpoints are reused. This example changes the Windows layout.

06 · The recalculation rule

Provenance decides. The author's word wins.

This generalises the no-clobber rule that touch re-propagation already follows (steps/repropagate.ts, spec 014), where base-derived and physical-suggested keys are refreshed and hand-set keys never are.

Downstream decision is…When an input changesWhat the author sees
extractedRun extract again against the new inputsThe new value, with "from <keyboard>"
default derivedRecompute, then applyThe updated value, marked as recalculated
asked, still validKeep. Run validate against the new inputsNothing changes
asked, no longer fitsKeep the value, flag it, and offer the recomputed value beside itA re-proposal (the existing reproposalNoticeStore), and never a silent overwrite
mixedRecompute the suggested items and keep the hand-set ones. An orphaned hand-set item is shown, not deletedThe author's edits stay, and the suggestions refresh around them
Gated off by the changeKeep the record and mark it inactive. It is not appliedThe step disappears. Switching back restores the answer
07 · What happens to each mechanism

Everything folds into decisions

Each fact is stored once. The decision store replaces the answer copies, and the overlays become the values of the decisions they record. A draft saves the starting point’s id and the decisions, and nothing else.

08 · What it would take

Six phases, each landing green

Phases 1 to 5 follow the 088 handoff. Phase 6 is new: recalculation needs every effect to be replayable, which the handoff does not yet require.

PHASE 1

A live decision store

  • Every completion writes Decision records
  • gatedBy reads the store, and decisionsFromTraversal goes
  • Drafts save per decision id, and old drafts migrate
Unlocks: one place that knows every answer and who gave it.
PHASE 2

Questions write through apply

  • The identity, track, project_name and help writes move into modules
  • VITE_KM_MUTATE_SEAM goes, and apply is the only path
  • apply returns a patch
Unlocks: question effects can be re-run.
PHASE 3

Galleries become modules

  • Each settles name gets a module, with the existing component as its renderer
  • In-place IR rewrites move into apply
  • Overlays become decision values, each item with its provenance
  • Every decision gets a log entry (the G7 gaps)
Unlocks: every effect is replayable. This is the largest phase.
PHASE 4

Steps derived from decisions

  • Placement comes from requires, and screens are merged by group
  • flowRefs and settles go
  • The parity tests prove "same order unless a requires says otherwise"
Unlocks: moving a decision takes one edit.
PHASE 5

Live extraction

  • Extraction runs after setup and seeds unanswered decisions
  • Setting up the working copy requires authoring-track (G7)
  • The acceptance test runs in the live wizard
Unlocks: the implied decisions in section 03.
PHASE 6 · NEW

Recalculate on change

  • Find the downstream closure from orderByDependencies's graph
  • Apply the provenance rule, generalising repropagate
  • Replay from a per-decision checkpoint
  • Show re-proposals for asked values that no longer fit
  • Stop saving the working copy: drafts hold decisions only
Unlocks: changing a decision updates the keyboard, and the keyboard can never disagree with its decisions.
09 · Open questions

Before the spec

Rebuild cost

Carve and mechanisms on a large starting point such as sil_euro_latin may be slow to rebuild, and a resumed draft rebuilds from scratch. Checkpoints cover edits. Resume may need a disposable cache that is thrown away whenever it disagrees with the decisions. Measure before phase 6.

Effects that aren't pure

Some reducers read live store state while they write. Each one has to become a function of (IR, value, inputs) before it can be replayed.

Opaque fragments

A RawKmnFragment is preserved, never edited. A replay must carry it through unchanged, not regenerate it.

D3 is unaffected

Recalculation is a write, not a validation, so it adds no timer. Validation runs once on the rebuilt copy, in the existing 300 ms cycle.

Changing the starting point

This is the widest possible closure: every extracted value is re-read, and asked answers are kept and re-checked. Decide whether that is a recalculation or a new project with the answers carried over.

Contracts stay put

The derived provenance and the patch type live in packages/studio. If either starts to reach packages/contracts, stop and check with the owner.
