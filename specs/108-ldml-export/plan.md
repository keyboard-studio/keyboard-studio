# Implementation Plan: LDML keyboard export

**Branch**: `108-ldml-export` (PR targets `main`) | **Date**: 2026-11-01 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification from [specs/108-ldml-export/spec.md](spec.md), with the normative
mapping [contracts/ldml-mapping.md](contracts/ldml-mapping.md) (profile `46`) and its delta
profile [contracts/ldml-mapping-49.md](contracts/ldml-mapping-49.md).

## Summary

Add a secondary **LDML export** to the Output page. One pure engine function classifies the
working copy against a **target profile** (`46` default, `49` TR35-only), and both consumers read
that classification:

- **Authoring time.** A memoised studio hook classifies the IR the live preview already parses
  from the **projected** `.kmn`. It joins the result into the one published findings array as
  `KM_LINT_LDML_*` Layer C warnings and hints, routed to the owning step. No timer is added
  (Art IV, D3).
- **Download time.** The Output page projects the working copy the way the other downloads do,
  parses the projected `.kmn`, touch layout and `.kvks`, classifies them, lowers the result to
  a keyboard3 document, and zips a Keyman LDML project with `LDML-EXPORT-REPORT.md`. The package
  is byte-deterministic (fixed zip mtime, no timestamps, ids derived from content).

The exporter writes its own deterministic XML serializer. It never imports a Keyman compiler at
runtime. Keyman's tooling is used only:

- in tests, for the FR-050 compile check against the **pinned** `@keymanapp/kmc-ldml@19.0.240-alpha`;
- in Story 5, behind the FR-070 trial, as a lazily loaded in-browser compile.

Profile `49` is validated against the CLDR 49 XSD (generated by CLDR from its DTD) and a TS implementation of the FR-052 TR35
rules, never against Keyman.

**Governing rule: one classifier, one walk.** Profiles are data (rows plus deltas). The IR walk,
the lowering and the findings builder never branch on a profile id, only on a row's status and
form (FR-061, SC-011).

## Technical Context

**Language/Version**: TypeScript 5 (repo pin), Node ≥ 22.19.0, pnpm 9.

**Primary Dependencies**:

- Existing: `@keyboard-studio/contracts` (KeyboardIR, TouchLayoutIR, KvksIR, LintFinding),
  `@keyboard-studio/engine` (codec `parse`, `parseTouchLayout`, `parseKvks`, `toZip`), fflate
  (already used by `toZip`), the studio's zustand stores, and Lingui.
- New engine **devDependencies**, all pinned:
  - `@keymanapp/kmc-ldml@19.0.240-alpha`, for the compile check;
  - `@keymanapp/common-types@19.0.240-alpha`, for `SchemaValidators.ldmlKeyboard3` (the engine
    cannot resolve it today);
  - `xmllint-wasm` (version pinned at implementation, at least two weeks old), for profile 49's
    CLDR XSD validation (it is XSD-only; research R28).
- No new runtime dependency on the default (Stories 1–4) path. Story 5 promotes `kmc-ldml` to a
  lazily loaded runtime dependency only if the FR-070 trial passes.

**Storage**: one new per-project output setting, `ldmlProfile`, saved in the working-copy snapshot
inside the existing draft envelope (the `chartPreference` precedent; no `DRAFT_VERSION` bump). One
new EPHEMERAL store field, `previewProjection`. See [data-model.md](data-model.md).

**Testing**:

- vitest unit tests beside each engine module.
- Engine corpus tests (`packages/engine/vitest.corpus.config.ts`, which needs `../keyboards`) for:
  - FR-050 compile against Keyman (profile 46);
  - FR-052 TR35 conformance and CLDR XSD validation (profile 49 and every touch form);
  - FR-051 keystroke equivalence;
  - SC-006 `ibono_chwerty` comparison;
  - SC-007 timing.
- Studio component tests for the Output panel, the routing and the persistence round-trip.
- One Playwright journey for the download.

**Target Platform**: the studio SPA (Vite, evergreen browsers) for export and findings, and Node in
CI for the Keyman compile, CLDR XSD validation and the equivalence harness.

**Project Type**: a feature inside the existing monorepo: a new engine module plus studio surfaces.

**Performance Goals**:

- Export ≤ 2 s for a keyboard of ≤ 2 000 rules (SC-007), measured on the corpus.
- The authoring-time classification is a synchronous memo that recomputes only when the
  preview's projected IR, the touch layout JSON, the `.kvks`, the resolved base layout or the
  profile changes. Its target is ≤ 50 ms on the same keyboards, measured.

**Constraints**:

- No host-disk writes (Art V).
- No second diagnostic timer (Art IV).
- Byte-identical package for an unchanged working copy and profile, in any interface language
  (FR-030).
- The report and the `.xml` comments are English (FR-030). Studio strings are in English and
  French (FR-019).
- LDML findings never gate non-LDML downloads or criteria (FR-016).

**Scale/Scope**:

- 34 finding codes: the 26 of the specify phase, six from the TR35 reread (`MODIFIER`, `MODIFIER_SIDES`, `BKSP_NO_CONTEXT`, `KEY_STORE`, `NEGATED_CLASS`, `CONTEXT_START`), and `BASE_DEADKEY` (row 2.26) and `NO_LOCALE` (row 4.16) from planning review. The R9 widening reuses `KM_LINT_LDML_NORMALIZATION`, and the
  set/save/reset reclassification reuses `KM_LINT_LDML_OPTION_STATE`.
- Corpus: the studio's existing fixtures, plus `ibono_chwerty`, `khmer_angkor`/`khmer_ldml` and
  one mnemonic keyboard.
- Spec-108 corpus scan: 50 of 1 036 `.kmn` files use `NewContext`/`PostKeystroke`.

## Constitution Check

*GATE: must pass before Phase 0 research. Re-checked after Phase 1 design (below).*

| Article | Verdict | Notes |
|---|---|---|
| I. Pattern schema locked | PASS | No `Pattern` change. The only contracts addition is optional: `LdmlProfileId` and the classification types live in the engine, not in contracts. `LintCode` already admits `KM_LINT_*`. |
| II. KeyboardIR spine | PASS, with a design rule | The export and the classifier read the typed IR: `KeyboardIR`, `TouchLayoutIR`, `KvksIR`. Neither touches `.kmn` text. Some constructs the IR keeps only as `raw` elements or `RawKmnFragment`s: `layer('x')` output, `match`/`nomatch` right-hand sides (`use(g)`), `platform(...)`, and rules made opaque by `set`/`save`/`reset`. The classifier **sub-classifies** those from the IR node's own `text`/`sourceText`, which is still reading the IR. FR-026's static layer evaluator depends on this. Every fragment yields exactly one item (FR-013); nothing is dropped. Parsing the projected `.kmn` uses the codec's `parse()` with no try/catch around it. A projection the codec cannot parse fails the LDML export with the codec's error, exactly as the other downloads fail. |
| III. State model | PASS, mapping stated | The profile choice is an **output setting**, not a decision (FR-062). It is saved in the working-copy snapshot, as `chartPreference` is, and is not written to the 088 DecisionSet or the 053 record, so no provenance mapping is needed. `previewProjection` is EPHEMERAL and is registered in `derivedSurfaceRegistry`. |
| IV. Validator layering, one D3 cycle | PASS | The LDML findings are Layer C, `KM_LINT_*`, built by a `useMemo` over inputs the existing cycle already produces (the oe2 and spec-080 precedent). There is no timer and no parallel validation path. The download reuses the pure classifier on the download projection; it starts no validation pass (FR-006). The Story 5 compile runs only on an author click, never in the cycle (FR-072). The classifier lives in the engine because depcruise forbids `keyboard-lint → engine` (research R12). That placement follows the oe2 precedent; it is not a fourth layer. |
| V. VirtualFS only | PASS | The package is built in memory and handed to the existing `triggerDownload`. The Story 5 compiled artifacts are staged into a clone (FR-076). |
| VI. Team boundaries | PASS | **Engine team**: the engine module, studio surfaces, CI. No pattern-library, survey-text, gallery-ordering, LLM-prompt or criteria-triage change. |
| VII. Out of scope | PASS | This is the secondary LDML export of the 2.2.0 amendment. The `.xml` never enters the KMN `.kmp` or the pull-request projection (enforced by a test on `buildOutputBundle` and the PR path). There is no LDML import, no emission-format switch, and no touch-first authoring. |
| VIII. House conventions | PASS | `[OK]`/`[WARN]` in harness console output. No issue numbers in shipped code or comments: upstream references such as #16868 stay in the spec and contracts, and the profile tables' lift conditions name the condition, not the issue. Commit titles use `feat(engine)`, `feat(studio)` and `feat(output)`. |
| IX. Decision registry | PASS | No new survey surface. The profile picker is an Output-page export option, which FR-062 states explicitly. Findings attach to existing step and question surfaces through `lintToQuestion.ts`. |
| X. Defaults are proposals | PASS | Profile `46` is the labelled default and is changeable in one interaction (SC-012). The base layout is the first entry of the existing ranking and is named in the report and the XML header. The author changes it through the survey answers that feed the ranking (clarify session); nothing is decided silently. |
| XI. Done means integrated | PASS, conditions | Done means: the download is reachable on the Output page, the findings are visible on their steps, and the CI corpus jobs are green and required. The Story 5 phases are conditional on the FR-070 trial. If the trial fails, Story 5 is withdrawn in the spec and tasks (owner: engine team; trigger: trial result), not left as a parked surface. Follow-ups in research carry an owner and a trigger. |

**Personal data**: none — no new store, recipient, category, or telemetry.

**Post-design re-check (after Phase 1)**: unchanged. The design adds:

**Structure Decision**: the classifier, the lowering, the serializer and the packager are one engine
module, `engine/src/ldml-export`. That module follows Art II and keeps them beside the codec they read.
It also keeps them out of `keyboard-lint` (depcruise) and loads them lazily, as the rest of the engine is, through
`services.ts`. Test tooling lives in `__testing__/` and is never exported from the barrel. That
keeps `kmc-ldml`, `common-types` and `xmllint-wasm` devDependencies only.

## Complexity Tracking

| Violation / cost | Why needed | Simpler alternative rejected because |
|---|---|---|
| Layer C findings computed in the engine rather than in `@keymanapp/keyboard-lint` | The exporter and the warnings must share one classifier (FR-012). The exporter is engine code, and depcruise forbids `keyboard-lint → engine`. | Duplicating the classifier in `keyboard-lint` would let warnings and the report drift. The oe2 detector and the spec-080 documentation checks already set this precedent. |
| Three new devDependencies (`kmc-ldml`, `common-types`, `xmllint-wasm`) | FR-050 requires Keyman's own compiler and schema. FR-052 and profile 49 require the CLDR schema; JS has no XSD validator of its own, and `xmllint-wasm` is libxml2 compiled to WASM. | A system `xmllint` fails on Windows developer machines. Re-implementing the schema check in TS would make the checker its own authority. |
| A test-only LDML interpreter (`__testing__/ldmlInterpreter.ts`) | FR-051 needs to run LDML. No JS runtime for LDML exists: Keyman Core WASM is not on npm and needs emscripten (research R22). | Building Core WASM in CI is a large toolchain cost for a test. The interpreter is limited to what the exporter emits, and the FR-050 compile gives a second, independent check. |
| A second projection consumer (the LDML download re-runs `projectWorkingCopyForOutput`) | The download must serialise the same projection the other downloads do (FR-003). | Sharing the preview's projection would export the preview id and identity, not the output identity. |
