# Contract: the optional `audit_label` flow-question field

A third piece of prose per flow question, in the catalog that already holds `prompt` and `help_text`. Content-owned values; engine-owned plumbing.

Governed by [specs/073-flow-question-i18n](../../073-flow-question-i18n/spec.md) and [specs/046-i18n-localization/contracts/catalog-format.md](../../046-i18n-localization/contracts/catalog-format.md). Nothing here overrides either.

## §1 The field

| | |
|---|---|
| Declared on | a question module's `definition.audit_label` |
| Catalog key | `content.flowQuestion.<id>.audit_label` |
| Type | `string`, optional |
| Cardinality | optional per question, optional per locale |
| Purpose | the author-facing name this question is given **in a decision headline** |

The `<id>` segment is slugified exactly as the other fields are — `slugifyIdSegment` replaces literal dots with `_`, and the runtime lookup in `lib/contentI18n.ts` applies the identical transform on the other end.

**When to author one.** Only where the question's `prompt` reads badly as a headline. `"Confirm your language's code"` is fine as-is; `"What is your language called in English?"` is not, and gets `"Language name (English)"`. Most questions need nothing. This sparseness is the point — the content cost is paid only where it buys legibility.

## §2 Extraction

`utilities/i18n-content-extract/extract.ts`'s `extractFlowQuestionStrings` walks four live phase registries (a/b/f/g) and emits `prompt`, `label`, `body`, `help_text`. Add `audit_label` to that field list.

- Emitted only when the value is a non-empty string after trim — the same guard the other four use.
- `mod.fixtures` and every control field remain unread.
- Demoted modules in `registry.reserve.ts` remain excluded (050 D2).

`content/i18n/en/flowQuestions.json` is regenerated by the extractor, never hand-edited. `pnpm run content-i18n-freshness` (`i18n-content-extract/cli.ts --check`) is what keeps the committed English file honest against a fresh extraction.

## §3 Parity — the rule that must change first

`flowQuestions.json` is in `PARITY_ONLY_FILES` (`utilities/content-i18n-lint/index.js:55`): its committed English file is the parity reference, and `checkTargetLocaleParity` compares **whole key sets** against every locale that has started the catalog. `content/i18n/fr/flowQuestions.json` exists, so French has started.

Adding one `audit_label` to one question under today's rule fails the lint for French immediately.

**Required change to `checkTargetLocaleParity`:**

```
a target-locale catalog MAY omit a key matching  content.flowQuestion.*.audit_label
                        without being reported as missing
```

- **Missing** `audit_label` in a target locale: allowed. The locale falls back to its own `prompt`, then to English — the existing `resolveContentString` contract, unchanged.
- **Extra** key in a target locale: still a failure, `audit_label` included. An override for a question English does not have is stale, not optional.
- Every other key: strictly parity-checked, exactly as today.

**Ordering obligation.** The lint change lands **before** the first `audit_label` value. Reversing that order turns CI red for a state the rule was always meant to permit.

## §4 Resolution at render

```
audit_label  ->  prompt  ->  FR-014 fallback prose
```

Resolved through `resolveContentString("flowQuestions", id, field, englishValue, i18n)` — the same seam `QuestionField.tsx` uses. Its "never blank" behaviour applies unchanged: a present-but-empty catalog value (a key shipped ahead of its translation) falls through to the English value rather than rendering blank.

The third step is reached only when a record references a question the build no longer has. A live question always has a prompt, so the fallback carries no routine traffic (FR-014).

## §5 Id stability

An id is a permanent handle. `content.flowQuestion.<id>.audit_label` is derived from the question's own id, so it inherits that question's stability: renaming the question orphans its translations, and that is a decision about the question, not about this field.

Changing an `audit_label`'s **wording** does not warrant a new key. Changing which question it belongs to does — because that is a different question.

## §6 Ownership

| Surface | Team |
|---|---|
| `definition.audit_label` values, `content/i18n/en/flowQuestions.json` | Content |
| Extractor field list, lint parity rule, resolution at render | Engine |

Per Constitution Article VI. The content team can add or remove an `audit_label` at any time without an engine change; the field's absence is always valid.
