# Implementation Plan: specRef anchors + spec-trace impacted-steps join

**Branch**: `km/specref-trace-join` (original) | **Date**: 2026-08-19 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification from `specs/031-specref-trace-join/spec.md`

## Summary

Add an optional `specRef` field to `StepBase` (`packages/studio/src/steps/types.ts`) and `QuestionModule` (`packages/studio/src/survey/types.ts`), populate it across the ~20 manifest step definitions and a representative sample of question modules, add a pure completeness check (`checkSpecRef`, mirroring the existing `checkInputsSatisfiableFromManifest` pattern), export a flat `manifest.specref.json` artifact via a `pnpm test`-time script, and extend `utilities/spec-trace/index.js`'s `buildDriftIssueBody`/`report` functions to read that artifact and surface an "Impacted steps" list. No new architecture — every extension point (the field-addition pattern, the pure-check pattern, the drift-issue-body builder) already exists and is mirrored, not invented.

## Technical Context

**Language/Version**: TypeScript 5.x (strict) for the studio side; the spec-trace extension stays plain CJS Node (no TS, matching the existing file).

**Primary Dependencies**: No new dependencies. `packages/studio/src/steps/types.ts`, `survey/types.ts`, `dashboard/completeness.ts`, `steps/manifest.ts`, and `utilities/spec-trace/index.js` are all edited in place.

**Storage**: `manifest.specref.json` is a generated, committed artifact (like other codegen outputs in this repo) — not vendored data, regenerated by a script.

**Testing**: vitest for the new `checkSpecRef` completeness check (colocated with `completeness.ts`'s existing tests); the spec-trace extension itself is exercised by whatever existing test coverage `utilities/spec-trace` has (confirm during tasks whether one exists; if not, this is Node CJS tooling outside the workspace's vitest configs per CLAUDE.md's "standalone utilities" note).

**Target Platform**: Studio SPA (the annotated types) + Node CLI (the spec-trace utility, CI-invoked).

**Project Type**: Cross-cutting annotation feature — touches the step/question-module type contracts, the manifest, a subset of question registries, and a standalone utility.

**Performance Goals**: N/A — annotations and a JSON artifact have no runtime cost; spec-trace already runs in CI's continue-on-error lane (FR-012), unaffected by generation timing beyond FR-010's staleness fallback.

**Constraints**: `utilities/spec-trace` MUST NOT import `packages/studio` code (CLAUDE.md architecture invariant + FR-007) — the `manifest.specref.json` artifact is the sole bridge, read as plain JSON. No CI hard-fail introduced (FR-012). No retroactive annotation of engine/contracts code (FR-013) or gallery editor components beyond their manifest entry (FR-014).

**Scale/Scope**: 2 type files edited (additive optional field), ~20 manifest step definitions annotated (FR-003, required — every entry), ≥10 question modules annotated across Phase A/B/F registries (FR-004, representative sample — optional field), 1 new completeness-check function + its test, 1 new artifact-generation script, 2 functions extended in `utilities/spec-trace/index.js` (`buildDriftIssueBody`, `report`).
