# Feature Specification: Crash reporting — an unrecoverable error becomes one actionable, author-anonymous GitHub issue

**Feature Branch**: `060-crash-reporting`

**Created**: 2026-08-05

**Status**: Draft

**Input**: User description: "When the studio SPA hits an unrecoverable error, capture a redacted crash report and file it as a GitHub issue using the server-side GitHub App installation token — never the user's OAuth token. One issue per fingerprinted bug; repeat occurrences add a comment. Redact author identity only; keyboard structural context is included because keyboard work is public and the report must be actionable. The studio has no ErrorBoundary today, so the client half is greenfield."

## Problem statement

The studio SPA has no crash telemetry and no recovery UI. Today, an uncaught error anywhere in the render tree, an unhandled synchronous throw, or an unhandled promise rejection produces a blank white screen and leaves no trace anywhere the team can find it. Two facts make this worse than an ordinary missing feature:

- **There is no ErrorBoundary to build on.** `grep -ri "errorboundary" packages/studio/src` returns nothing. `main.tsx`'s `mountApp()` and `mountCallbackScreen()` have no try/catch around them either — a throw before `createRoot(...).render(...)` (for example `requireRoot()` at [main.tsx:18-24](../../packages/studio/src/main.tsx#L18), or a rejected `localeReady` at [main.tsx:33](../../packages/studio/src/main.tsx#L33)/[:98](../../packages/studio/src/main.tsx#L98)) is a fully uncaught exception with zero UI and, again, zero record. The client half of this feature is genuinely greenfield, not an extension of an existing pattern.
- **There is no build identifier anywhere at runtime.** `packages/studio/package.json` declares `"version": "0.1.0"`, but nothing surfaces it — no `import.meta.env.VITE_APP_VERSION`, no Vite `define`, no reference to `VERCEL_GIT_COMMIT_SHA` anywhere in `packages/studio` (confirmed by search across `vite.config.ts`, `vite-env.d.ts`, and every `lib/*` env-flag file). A filed crash report with no build identifier is not actionable — a maintainer cannot tell whether a reported bug is already fixed. This is on the critical path, not an edge case (group L).

### Observed defects (evidence for the requirements below)

Audited against `main` at commit `6e136d30`, 2026-08-05.

- **E-1 — no ErrorBoundary, no window-level handlers, no telemetry of any kind.** Confirmed by grep as above. A render throw currently degrades to a blank page with no console signal beyond whatever React itself prints in dev mode (stripped in production).
- **E-2 — no build metadata surfaces at runtime.** As above; this feature's Vite `define` (group L) is genuinely new infrastructure, not a wiring fix.
- **E-3 — identity currently flows in exactly one direction: into output, never stripped.** `packages/contracts/src/attribution.ts` defines `Attribution.authorName` / `authorEmail?` / `copyrightHolder` ([attribution.ts:12-38](../../packages/contracts/src/attribution.ts#L12)) precisely so they can be embedded in commits and PR bodies — `github-pipeline.ts`'s `buildCommitMessage` / `buildPrBody` do so deliberately ([github-pipeline.ts:128-154](../../utilities/oauth-backend/src/github-pipeline.ts#L128)). That is correct behaviour there, and it confirms there is no existing "strip PII" helper to model a redactor on, and no test asserting identity's *absence* anywhere in the codebase. This feature's redaction step (group D) is new, not adapted.
- **E-4 — a real conflict between "reuse the decision log for context" and the client self-containment requirement, found while drafting this spec, not caught by any prior probe.** `packages/studio/src/decisions/decisionLogStore.ts` — the store holding the append-only decision record — has a **static value import** of `@keyboard-studio/engine`: `import { normalizeDecisionRecord } from "@keyboard-studio/engine";` at [decisionLogStore.ts:37](../../packages/studio/src/decisions/decisionLogStore.ts#L37). Roughly 90 files across `packages/studio/src` hold a similar static dependency on that package (`grep -rn 'from "@keyboard-studio/engine"'` — a representative sample includes `workingCopyStore.ts`, `impact.ts`, `snapshotSource.ts`, `draftPersistence.ts`), none of them behind a dynamic `import()`. If a crash-capture module imported `decisionLogStore.ts` directly to read "the tail of the existing decision log" (a piece of structural context this feature is asked to carry), its own reachable import graph would include a module that imports `@keyboard-studio/engine` as a value — which is exactly what the client self-containment requirement (group B) forbids and exactly what its own gating test would need to catch. This is resolved in group E: the crash module never imports the store; the *caller* (which already runs inside the fully-loaded app and already depends on the engine elsewhere) reads the store and passes the tail in as plain data.
- **E-5 — a third hand-rolled GitHub REST caller is a known-fragile pattern, already flagged twice.** `packages/engine/src/output/github.ts` (Option A, user-token fork+PR) and `utilities/oauth-backend/src/github-pipeline.ts` (Option B, org-token managed PR) are an explicitly documented vendored pair — `github-pipeline.ts:9`: *"Vendored from packages/engine/src/output/github.ts — keep in sync."* Extracting a shared client into a workspace package is a non-starter for the server side: any module in `api/**`'s reachable graph that imports a `@keyboard-studio/*` package as a *value* breaks bundle safety the same way `@keyboard-studio/contracts`'s JSON re-exports do ([api/bundle-safety.test.ts:1-30](../../api/bundle-safety.test.ts#L1)). This feature adds a third caller; group I resolves how, deliberately, rather than by silent copy-paste.

## Clarifications

### Decisions settled before this spec was drafted

These were resolved by the user and by `/km-lead` in the cycle-1 research that precedes this document. They are written here as requirements, not options — see the cited requirement group for each.

- **Q: Whose GitHub credential files the issue?** → A: The server-side GitHub App installation token, exclusively — never the user's OAuth token. Crashes routinely happen before sign-in, and filing under the user's identity would be an unauthorized outward write on their behalf. (Group I.)
- **Q: What gets redacted?** → A: Author identity only — `Attribution.authorName` / `authorEmail` / `copyrightHolder`, every field of `IdentitySession` (`packages/studio/src/lib/identity.ts`), and anything sourced from an OAuth profile. Keyboard content is public — "the repos are public, we need enough references to handle the bug, but not necessarily identifying information" (user, cycle 1) — so structural keyboard context ships by default. (Group D.)
- **Q: How many issues per bug?** → A: One issue per fingerprinted bug. A repeat occurrence adds a comment to the existing issue rather than opening a new one; a closed match reopens with a `regression` label. (Group J.)
- **Q: Search API or REST for dedupe lookup?** → A: REST, via a `crash/fp-<hash12>` **label**, queried through `GET /repos/{owner}/{repo}/issues?labels=crash/fp-<hash>&state=all`, explicitly **not** `GET /search/issues`. The Search API has a documented indexing lag (seconds to minutes before a newly-created or newly-labelled issue becomes findable) and a much lower rate limit (30 req/min, shared across the whole installation) than the ordinary REST budget (5,000/hr). A label is primary issue metadata, not a derived index, so the REST lookup is strongly consistent and draws on the larger budget. This is a **rationale worth preserving in the code as a comment**, not just here — a future reader who "optimizes" this back to the Search API would silently reintroduce both the lag and the rate ceiling. The fingerprint is also embedded in the issue body as a trailing HTML comment (`<!-- crash-fingerprint: <hash> -->`) for human auditability, but the label is the only thing the lookup reads. (Group J.)
- **Q: How auto vs. confirmed is sending?** → A: Auto-send with a non-blocking notice, never a confirm gate. The report is filed immediately; the author sees a banner naming that a report was sent, with a link to the filed issue. No dialog blocks the crash-recovery path on a decision the author is in no state to make well. (Group H.)
- **Q: How much keyboard context ships?** → A: Structural context only — keyboard id, BCP47 tags, the current step id, counts (key count, exemplar count), and the tail of the existing decision log. **No** full VirtualFS snapshot; no raw file contents. (Group E.)
- **Q: Which repository receives the issues?** → A: A new, dedicated `keyboard-studio/crash-reports` repository — not `keyboard-studio/keyboards`, whose issue tracker is a curated content-review surface that crash noise would pollute. The repository does not exist yet; its creation, a **second, dedicated GitHub App**'s creation and installation onto it (**revised in review cycle 2, P0-2** — not a permission bump on the existing managed-PR App, see Prerequisites), and a Vercel Firewall rate-limit rule are manual prerequisites, listed below, not code this feature ships.
- **Q: Where does the fingerprint live and who computes it?** → A (**revised in review cycle 2 — see the note directly below**): **Server-side, authoritatively.** The client POSTs structured raw fields — `kind`, the unnormalized `message`, and raw `stackFrames[]` (function, module path, line, column) — and the server performs the canonicalization (message normalization, chunk-hash-suffix stripping, top-3-5-frame truncation, line/column dropping) and computes the SHA-256 itself (Group I). The client also computes a fingerprint locally, by the identical algorithm, but strictly for its own per-session dedupe cache (Group C, Group K) — it is never sent to the server and never trusted for lookup or mutation.

  **Why this was revised.** The cycle-1 design (client-computed, server-trusts-the-hash-verbatim) has a real vulnerability: the fingerprint is a public label, visible on every issue by construction, so secrecy was never available as a mitigation, and a client that can compute a hash can also fabricate one — trusting it for both lookup *and* mutation (comment, reopen-as-regression) lets a hostile caller land a forged report on any issue whose label it can read. Moving canonicalization and hashing server-side closes this by construction: a forged report can only ever land on the issue its own content actually hashes to, because the server derives the hash from the content itself, never from a client-asserted identifier. The original rationale for client-side hashing was that the server lacks source maps to resolve minified stack positions — that rationale does not hold, because canonicalization operates on already-resolved structured fields (`function` name, `modulePath`, line, column) the client extracts from its own `Error.stack`, not on raw minified bytes; no source-map decoding happens on either side. This is deterministic string work over structured input, and the server is exactly as capable of it as the client. See FR-081a-FR-081f for the precise algorithm and a worked example. (Groups C, I.)
- **P0 (added by `/km-lead`, no probe caught it originally): the crash-capture path must not depend on the engine.** `computeSha256Hex` already exists at [packages/engine/src/codec/hash.ts:14](../../packages/engine/src/codec/hash.ts#L14) and is the obvious thing to reuse for the fingerprint hash — **this spec explicitly forbids that.** The engine is loaded through a dynamic `import()` in `loadEngine()` ([useKeyboardArtifact.ts:45-61](../../packages/studio/src/hooks/useKeyboardArtifact.ts#L45)), and a failed engine-chunk load is one of the crash classes this feature exists to report. A reporter that depends on the chunk that just failed to load cannot report that failure. The entire crash-capture path — local (session-cache-only) fingerprint hashing, redaction, payload construction, POST — MUST be self-contained in the studio's main bundle, with no dynamic import and no `@keyboard-studio/engine` dependency anywhere in its own reachable graph. `crypto.subtle.digest` is inlined directly; `computeSha256Hex` is not imported. This is testable and MUST be tested (group B). This P0 is unaffected by the cycle-2 revision that moves the *authoritative* fingerprint computation server-side (see the fingerprint clarification above): the client still needs its own local hash to key its per-session dedupe cache (group K), and that local computation is exactly what this P0 requires to stay self-contained.

### A conflict found while drafting this spec, and how it is resolved

- **Q: The decision-log tail is wanted as context, but reading it naively breaks the P0.** → A (E-4 above): the crash-capture module never imports `decisionLogStore.ts` or any store that reaches `@keyboard-studio/engine`. Instead, the **call site** — the ErrorBoundary fallback, the `window.onerror` handler, the `unhandledrejection` handler — reads `useDecisionLogStore.getState()` itself (it already runs inside the fully-mounted app, which already depends on the engine dozens of times over) and passes the last N entries into the crash module's payload-builder as a plain data argument. The crash module's own file therefore has zero import edges toward the engine, and the existing decision-recording path is untouched.
- **Q: What does "a short undo/delete window" (user, cycle 1, decision 6) mean given GitHub does not expose issue deletion to a REST-scoped installation token?** → A: GitHub's issue-deletion capability is a GraphQL `deleteIssue` mutation gated to organization-repo admins, not something an installation token with `issues:write` can do. "Delete" is therefore realized as **retract, not erase**: while the notice banner is visible, an "Undo" affordance is offered; activating it, for a report whose action this session was `"created"`, closes the issue and adds a `"retracted by reporter"` comment (never a silent removal — the record that a report existed stays visible for maintainers, just marked withdrawn). For a report whose action was `"commented"` on someone else's pre-existing issue, "Undo" removes only the comment this session added — the issue itself is not this session's to close. This is new design, not sourced from any cycle-1 probe; it is scoped narrowly (group H) precisely because no probe examined it.

## Prerequisites (manual, non-code — block implementation)

These are GitHub Settings and Vercel dashboard actions for the repository owner. None of them is a code task, and the server route cannot function until steps 1-4 are done. **Revised in review cycle 2 (P0-2):** the original draft reused the managed-PR pipeline's existing GitHub App with a widened permission set. That design was rejected — a crash-reporting endpoint is public and unauthenticated by nature, so a flood of distinct fingerprints would exhaust the *shared* installation's 5,000/hr REST budget, starving the managed-PR submit path that budget also serves. The fix is a **second, independent GitHub App**, scoped to `issues:write` only and installed only on the new repository, so abuse of this endpoint cannot touch the managed-PR pipeline's budget or its `contents:write`/`pull_requests:write` blast radius at all.

1. **Create the `keyboard-studio/crash-reports` repository.** Public, empty, no special settings beyond what any other repository in the org has.
2. **Create a second, dedicated GitHub App** (e.g. "Keyboard Studio Crash Reports") — **not** a permission change to the existing managed-PR App. Declare exactly one permission: `issues: write`. Do not grant `contents:write` or `pull_requests:write` — this App has no reason to touch repository contents or pull requests, and not granting them removes that capability from the public endpoint's blast radius entirely, independent of any code-level bug.
3. **Install the new App only on `keyboard-studio/crash-reports`.** GitHub Settings → Installed GitHub Apps → the new app → Configure → repository access → `crash-reports` only. Per the existing installation-token constraint the codebase already documents for the *other* App ([github-pipeline.ts:94-104](../../utilities/oauth-backend/src/github-pipeline.ts#L94)), an installation token has *"no cross-repo contributor affordance"* — the same constraint applies to this new App. Attempting to file against an uninstalled repository fails with a 403 ("Resource not accessible by integration"), which this feature maps to the existing `submission_unavailable` vocabulary rather than a distinct error class.
4. **Generate the new App's private key and set three new environment variables**, parallel to but distinct from the managed-PR App's: `CRASH_REPORT_APP_ID` / `CRASH_REPORT_APP_PRIVATE_KEY` / `CRASH_REPORT_APP_INSTALLATION_ID`. These are read by a new, dedicated token minter (Group I, FR-085) and MUST NOT be the same values as `GITHUB_APP_ID` / `GITHUB_APP_PRIVATE_KEY` / `GITHUB_APP_INSTALLATION_ID` — those remain exclusively the managed-PR pipeline's credentials. The target owner/repo (`keyboard-studio/crash-reports`) is a source constant (mirroring `UPSTREAM_OWNER` / `UPSTREAM_REPO` in `github-pipeline.ts:104-105`), not an environment variable.
5. **Configure a Vercel Firewall / WAF rate-limiting rule on the crash-report path** (`/report/crash`, rewritten to `/api/report/crash`). This is a dashboard/IaC configuration action, not code — it needs no KV store and composes with, rather than replaces, the code-level flood-control layers in group K. Starting values (adjustable by the repository owner without a deploy): rate-limit by IP, threshold **20 requests per 60 seconds**, action **deny with 429** for 10 minutes on breach. This bounds the cost of a single-source flood before it ever reaches the code-level global-creation-cap check (FR-106) or the App's own rate budget.

Until steps 2-4 are complete, the server-side "not configured" state (503, group I) covers only the case where the `CRASH_REPORT_APP_*` env vars are absent entirely (mirroring the managed-PR route's existing `appConfigured` gate, [server.ts:142](../../utilities/oauth-backend/src/server.ts#L142)). A repository that exists but is not yet installed on is **not** distinguishable from env alone — the server cannot introspect installation-level repository access without making the API call — so that state surfaces through the ordinary 401/403 → `submission_unavailable` mapping, not a fourth configuration state. Step 5 (the Vercel rule) has no server-observable "not configured" state at all — its absence is a residual risk, not a detectable one; see FR-106's discussion of the residual-risk owner.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - A crash becomes one actionable issue, with no author identity in it (Priority: P1)

An author's browser throws inside a component render. Without them doing anything, a redacted crash report is filed as a new GitHub issue in `keyboard-studio/crash-reports`, carrying the error, the build id, and structural keyboard context — but nothing that identifies the author. A recovery screen appears with a link to the filed issue.

**Why this priority**: This is the entire feature. Every other story either protects this one from noise (US2, US3) or extends its reach to harder crash classes (US4, US5).

**Independent Test**: Force a render throw in a test build, assert exactly one issue is created against a stub GitHub API with the expected redacted body and label, and assert the recovery screen shows a link to it.

**Acceptance Scenarios**:

1. **Given** an author mid-walk with a working copy carrying identity answers, **When** a render throw occurs, **Then** a GitHub issue is filed containing the keyboard id, BCP47 tags, current step id, and decision-log tail, and containing none of `authorName`, `authorEmail`, `copyrightHolder`, or any `IdentitySession` field.
2. **Given** the same crash, **When** the report is sent, **Then** it carries a build identifier (commit SHA) sufficient for a maintainer to tell which deploy produced it.
3. **Given** the filed issue, **When** the author looks at the recovery screen, **Then** a link to that exact issue is present and a heading announces that a report was filed.
4. **Given** an author who is not signed in to anything, **When** the crash occurs, **Then** the report still files successfully — the credential used is the server's installation token, never anything tied to the author's own session.

---

### User Story 2 - Repeat crashes do not spam the tracker, and regressions are distinguishable from fresh occurrences (Priority: P1)

The same bug crashes a second author's session an hour later. Instead of a second issue, the existing one gets a comment recording the new occurrence. Months later the bug is reintroduced and crashes again after its issue was closed as fixed; that issue reopens with a `regression` label rather than silently staying closed or spawning a duplicate.

**Why this priority**: Without this, a single flaky bug across many sessions turns the tracker into noise within hours, defeating the whole point of "actionable."

**Independent Test**: File the same fingerprint twice against a stub GitHub API; assert the second call comments rather than creates. Close the stub issue, file the fingerprint a third time; assert it reopens with `regression` added and a comment is posted.

**Acceptance Scenarios**:

1. **Given** an existing open issue labelled `crash/fp-<hash>`, **When** the same fingerprint crashes again, **Then** a comment is added to that issue and no new issue is created.
2. **Given** an existing *closed* issue with that label, **When** the same fingerprint crashes again, **Then** the issue is reopened, a `regression` label is added, and a comment records the new occurrence.
3. **Given** the dedupe lookup itself fails (network error or 5xx from GitHub on the label query), **When** a crash is reported, **Then** the server creates a new issue anyway rather than dropping the report — losing a crash report is worse than an occasional duplicate.
4. **Given** two near-simultaneous first-time crashes with the same fingerprint (a race on the "no match yet" read), **When** both requests proceed to create, **Then** both issues may exist, and this is accepted as a rare, self-healing duplicate rather than something the system takes on distributed-locking cost to prevent.

---

### User Story 3 - A stale deployment recovers silently and never gets reported (Priority: P1)

An author has a tab open from before a deploy finished. Vite's chunk hashes changed underneath them; their next dynamic import 404s. The app reloads once automatically and continues working. No crash report is ever filed for this.

**Why this priority**: Without this carve-out, every deploy floods the tracker with an identical, uninteresting "chunk not found" report from every tab that happened to be open at deploy time — the exact opposite of "actionable."

**Independent Test**: Simulate a `vite:preloadError` (and, separately, the raw-`import()` failure message pattern) and assert a single `location.reload()` occurs and no POST to the crash endpoint is made.

**Acceptance Scenarios**:

1. **Given** a `vite:preloadError` event, **When** it fires, **Then** `event.preventDefault()` is called (so it does not also surface as an unhandled rejection), a `sessionStorage` timestamp is checked, and if the last such reload was more than 60 seconds ago, the page reloads once and nothing is reported.
2. **Given** `loadEngine()`'s underlying `import()` rejection ([useKeyboardArtifact.ts:45-61](../../packages/studio/src/hooks/useKeyboardArtifact.ts#L45)) matching the dynamic-import-failure pattern — preserved and forwarded per FR-005a rather than swallowed into the catch clause's synthetic `null` return and the caller's own generic message (P0-3) — **When** it is classified, **Then** the same stale-chunk handling applies before any "report this" affordance can appear.
3. **Given** a reload already happened within the last 60 seconds and the same class of failure recurs, **When** it is detected, **Then** the automatic reload does **not** repeat — this is now classified as genuinely unreachable (US5), not stale, and filing is allowed.

---

### User Story 4 - The reporter survives what it reports (Priority: P2)

The **compile/scaffold/output engine surface** — `compile`, `fetchKeyboardSourceToVfs`, `init`, `createScaffolderService`, `buildKmp`, `toZip`, all fetched together via `loadEngine()`'s dynamic `import()` — fails to load: a genuinely broken deployment, not a stale tab. The crash reporter, whose own source-level import graph never references that surface, still captures and files the failure.

**Why this priority**: This is the P0's payoff in user terms. Without it, the one crash class most worth reporting (a broken deploy) is exactly the one the reporter would be unable to report, silently. **Scope of the guarantee, now verified against a real build (settled in review cycle 3, resolving QC review cycle-1 P1-1):** a `pnpm build` chunk inspection confirms `packages/studio/dist/index.html` loads **exactly one** entry script (`index-BgCc6H-5.js`, ~6.9 MB / ~1,562 kB gzip, containing React, zustand, and every store including `workingCopyStore`) with **no** `modulepreload` links — i.e. the reporter's own code, bundled into that single entry chunk, is already parsed and running well before any `loadEngine()` call. `loadEngine()`'s dynamic `import()` fetches a genuinely separate, lazily-loaded chunk (`index-Cgmd-NEY.js`, ~61 kB / ~21.9 kB gzip) that carries exactly the compile/scaffold/output surface named above; every reference to it in the built output is inside an `import()` call, with zero static `from` declarations reaching it. So the premise QC-P1-1 challenged was overscoped, not refuted: "the engine" is not one atomic lazy dependency. `workingCopyStore.ts:26`'s two named imports (`detectMarkInputOrderFromImport`, `renameTouchKey`) are small, pure helpers that Rollup/terser duplicates directly into the entry chunk — those identifiers appear in the entry chunk's output but not as a static dependency edge onto the lazy chunk — while the heavier compile/scaffold/output surface stays a real, independently-fetchable chunk. **The load-bearing fact for this story:** at the moment that lazy chunk fails to load, the entry chunk — and the crash reporter inside it — is already running, so a failure there cannot take the reporter down with it. This also confirms the Group B self-containment requirement (FR-010-FR-014) earns its keep for a documented reason rather than an assumed one: even though a couple of small pure helpers are duplicated into the eager bundle regardless of this feature, the reporter's own source-level import graph staying clear of `@keyboard-studio/engine` (verified by FR-013/FR-132, independent of how Rollup chunks anything) is what guarantees it survives the *heavier* surface's failure, not an accident of how the current build happens to chunk two small functions. **Confidence level:** the duplication mechanism above is inferred from reading the built, minified output (chunk sizes, script tags, presence/absence of identifiers) rather than from a Rollup chunk-graph manifest; see the Test Surface entry for what would raise that confidence.

**Independent Test**: Statically analyze the crash-capture module's import graph (mirroring `api/bundle-safety.test.ts`'s walker) and assert it reaches zero modules that import `@keyboard-studio/engine` as a value, directly or transitively. Separately, simulate a compile/scaffold/output engine-surface load failure past the stale-chunk carve-out and assert a report is still filed.

**Acceptance Scenarios**:

1. **Given** the crash-capture module's source files, **When** their import graph is walked, **Then** it contains no edge, direct or transitive, into `@keyboard-studio/engine` — including no edge into `decisionLogStore.ts` or any other module that itself imports the engine.
2. **Given** a compile/scaffold/output engine-surface load failure that has already failed the stale-chunk reload once, **When** it fails again, **Then** the crash-capture path runs and successfully computes a fingerprint, builds a redacted payload, and POSTs it — using none of the failed chunk's exports.
3. **Given** the same failure, **When** the fingerprint is computed, **Then** `crypto.subtle.digest` is called directly inside the crash module; `computeSha256Hex` from the engine is never imported or called.

### User Story 5 - A crash before React ever mounts still gets reported (Priority: P2)

A throw happens inside `mountApp()` before `createRoot(...).render(...)` runs — no component tree exists, so no ErrorBoundary could ever have caught it. A plain, dependency-free message appears, and a bare best-effort report is still sent.

**Why this priority**: This is the one crash class an ErrorBoundary structurally cannot reach. Skipping it would leave the single least-recoverable failure mode invisible.

**Independent Test**: Force `requireRoot()` or the `localeReady` await to throw/reject before `createRoot` runs in a test harness; assert a static fallback renders from `index.html`'s own markup (no React, no i18n) and a bare `fetch` POST is attempted.

**Acceptance Scenarios**:

1. **Given** a throw before React mounts, **When** it is caught by a top-level try/catch in `main.tsx`, **Then** a plain, English-only, dependency-free `<div>` already present in `index.html` is revealed — no lazy import, no catalog lookup.
2. **Given** that same failure, **When** the fallback reveals, **Then** a best-effort `fetch` POST of `{ message, stack, appVersion }` is attempted with a short timeout, and its failure is swallowed silently — nothing here can throw a second time.
3. **Given** this path fires, **When** the payload is compared to an ordinary in-app crash report, **Then** it is deliberately smaller (no fingerprint canonicalization, no decision-log tail, no redaction pipeline) because none of that machinery can be assumed to exist yet.

---

### User Story 6 - An author can retract a report they just triggered (Priority: P3)

Immediately after a report is auto-sent, the author realizes the crash was caused by something they don't want on the public tracker (unlikely, given redaction, but the affordance exists) and clicks "Undo" on the notice banner before it disappears.

**Why this priority**: Smallest story in the set; it is a courtesy affordance on top of a feature that already auto-sends by design, not a safety-critical path.

**Independent Test**: File a report, invoke retract within the window, and assert the issue is closed with a retraction comment (for a `"created"` action) or the added comment is removed (for a `"commented"` action).

**Acceptance Scenarios**:

1. **Given** a report whose action was `"created"`, **When** the author retracts it within the notice window, **Then** the issue is closed and a `"retracted by reporter"` comment is added — the issue is never truly deleted (GitHub does not expose deletion to an installation token).
2. **Given** a report whose action was `"commented"` on a pre-existing issue, **When** the author retracts it, **Then** only the comment this session added is removed; the issue itself, which predates this session, is untouched.
3. **Given** the notice banner has been dismissed or its window has elapsed, **When** the author looks for the retract affordance, **Then** it is gone, and the report stands.

### Edge Cases

- **Burst of duplicate issues from a race.** Two near-simultaneous first occurrences of the same fingerprint both read "no match" before either has created its issue. Both proceed to create. Accepted as a rare, self-healing duplicate (US2-4) rather than adding distributed locking for a v1 feature with no KV store in this stack.
- **Crash loop.** The same fingerprint recurs dozens of times in minutes (e.g., a render loop that re-throws on every re-render attempt). The client's per-session fingerprint cache stops most attempts before they POST; the server's stateless comment cap (derived from the matched issue's own `comments` count and `updated_at`, no external store) stops the rest from flooding the issue once the cache is bypassed (new tab, new session). See group K.
- **GitHub itself is down or returns 5xx.** Mapped to `502 submission_unavailable` / `upstream_error`, the same vocabulary `github-pipeline.ts` already uses. The client never surfaces this as an actionable error to the author — they are already dealing with the original crash.
- **The crash-reporting GitHub App is not configured at all** (no `CRASH_REPORT_APP_*` env vars — a dev or preview deploy without secrets). Mapped to `503 reporting_not_configured`, mirroring the managed-PR route's existing `submission_not_configured`. (Renamed from `GITHUB_APP_*` in review cycle 2 — P0-2 gives this feature its own, separate App and env-var set; see Prerequisites.)
- **The dedupe lookup itself fails** (network error or 5xx on the label `GET`). Fails **open** — proceeds to create a new issue — rather than closed, because losing a crash report silently is worse than an occasional duplicate (US2-3).
- **A genuinely unreachable chunk that is not a stale deploy** (CDN outage, CORS misconfiguration, an ad-blocker). Distinguished from a stale deploy by the reload-window check: if a reload already happened within 60 seconds and the same failure class recurs, it is no longer treated as stale, and filing is allowed (US3-3, US4).
- **`loadEngine()`'s catch clause masking its own rejection (P0-3).** Verified against real code ([useKeyboardArtifact.ts:58-60](../../packages/studio/src/hooks/useKeyboardArtifact.ts#L58), [:533-538](../../packages/studio/src/hooks/useKeyboardArtifact.ts#L533)): the catch clause swallows the real `import()` rejection into `null`, and the caller throws an unrelated synthetic string instead. Because FR-051's classifier can only ever see whatever text reaches it, and that text was always the synthetic string regardless of cause, a genuine stale-chunk engine failure fell through the carve-out and would have filed an issue — exactly what User Story 3 exists to prevent, and something the original draft of this spec did not catch. Fixed by FR-005a: the original rejection is preserved and forwarded to the classifier before FR-051's pattern match runs.
- **A distributed creation flood exhausting the crash-reports App's own budget (P0-2).** Many distinct fingerprints from many source IPs, each below the per-IP Vercel Firewall threshold (Prerequisites #5), could still collectively approach the crash-reporting App's own 5,000/hr installation budget. FR-106's stateless global-creation-cap check bounds this without new infrastructure; residual risk beyond that cap is named, with an owner, at FR-106.
- **Regression-reopen spam on a closed issue (P0-A, new in review cycle 4).** A closed issue's own content — `message`, `stackFrames`, and the fingerprint itself (echoed in the body, FR-092) — is public. A caller who copies it verbatim and resubmits could otherwise force a reopen-plus-`regression`-label call on every hit, since the review-cycle-2 wording exempted that state-change from every flood-control layer (FR-102 governs comments only; FR-106 gates creates only). Fixed by FR-095a's cooldown: the reopen still always happens on the first hit after a close (the regression signal is never dropped), but repeat hits within `CRASH_REPORT_REOPEN_COOLDOWN_MS` are suppressed rather than each forcing another reopen call.
- **An unreachable global creation cap (P0-5, new in review cycle 10).** FR-106's review-cycle-2 wording paired a `per_page=100` probe with a cap of 200. GitHub caps `per_page` at 100, so the observed count could never reach the threshold and the requirement's own "last line of defence" was inert in production while reading as implemented. It survived nine review cycles because the test stub ignored `per_page` and returned a 200-element page no real API could produce — the assertion passed on a fixture, not on a behaviour. Fixed by FR-106's pagination amendment, with the page bound derived from the cap so the two cannot drift apart again, and by requiring cap-probe stubs to page.
- **Retraction of someone else's report (P0-6, new in review cycle 10).** `POST /report/crash/retract` is public and unauthenticated, and its original body named its own target (`issueNumber`, `action`, `commentId`). Issue numbers in `keyboard-studio/crash-reports` are sequential and publicly visible, and FR-074's 30 s window is client-side UI state, so any anonymous caller could close — or delete a comment from — an arbitrary crash report indefinitely, at no cost. This is P0-1's defect class on a second route: a forgeable field trusted because the legitimate client happens not to forge it. Fixed by FR-074a: the three fields leave the wire schema entirely and are carried inside a signed, expiring capability token the server itself minted, so the route has no caller-supplied target left to trust.
- **A pre-mount report 400ing instead of filing (P0-B, new in review cycle 4).** The review-cycle-2 schema rewrite made `kind` a required enum field, but the pre-mount path (FR-062) never sends `kind` — every pre-mount report failed validation, silently disabling the one crash class an ErrorBoundary structurally cannot catch. Fixed by making `kind` optional in `CrashReportBodySchema` (FR-081), server-defaulted to `"pre-mount"` (FR-006).
- **Crash-in-the-crash-reporter.** The capture-and-send path itself must not be able to produce a second uncaught exception. The entire path — capture, fingerprint, redact, build payload, POST — is wrapped so that any internal failure is swallowed silently (at most pushed to the breadcrumb ring, which has no reader once the reporter itself has failed) rather than escaping to become a second unhandled rejection that could re-enter the same handler.
- **An optional field is genuinely absent** (no BCP47 tags yet, no working copy instantiated, the crash happens on the Welcome screen before any project exists). The payload's structural-context fields are all optional; their absence is represented, not fabricated as a zero or an empty placeholder that could be misread as "confirmed empty."

## Requirements *(mandatory)*

### A. Capture surfaces and classification

- **FR-001**: The system MUST install exactly one React `ErrorBoundary`, mounted inside `AppRoot`'s `<I18nProvider>` ([AppRoot.tsx](../../packages/studio/src/AppRoot.tsx)) so its fallback can use the message catalog and so it covers every subtree `main.tsx` mounts (`StudioShell`, `LintDemo`, `OAuthCallbackScreen`) with one boundary, not three.
- **FR-002**: The system MUST install a `window.onerror` handler to capture synchronous errors outside the React tree (worker callbacks, non-React event handlers) and file a report for them.
- **FR-003**: The system MUST install an `unhandledrejection` handler to capture un-awaited promise rejections and file a report for them.
- **FR-004**: The system MUST install a `vite:preloadError` handler that calls `event.preventDefault()` and routes into the stale-chunk carve-out (group F) rather than the ordinary filing path — without the `preventDefault()` call, the same failure would also surface as an unhandled rejection and could be double-counted.
- **FR-005**: `useKeyboardArtifact`'s existing `Stage: "error"` state ([useKeyboardArtifact.ts:165-182](../../packages/studio/src/hooks/useKeyboardArtifact.ts#L165)) MUST NOT auto-file a report on every occurrence — `fetch` and `compile` errors there are frequently transient or environmental and already have a modelled Retry UX. The one exception is `loadEngine()`'s own catch clause, which MUST be checked against the stale-chunk pattern (group F) before any filing affordance can appear.
- **FR-005a** (P0-3, added in review cycle 2 — verified against real code): `loadEngine()`'s `catch` clause ([useKeyboardArtifact.ts:58-60](../../packages/studio/src/hooks/useKeyboardArtifact.ts#L58)) currently swallows the real `import()` rejection entirely and returns `null`; its caller ([useKeyboardArtifact.ts:533-538](../../packages/studio/src/hooks/useKeyboardArtifact.ts#L533)) then throws a synthetic, fixed string (`"Engine failed to load — check browser console for WASM errors."`) that bears no relationship to the original failure. Because FR-051's stale-chunk regex can only ever see whatever text reaches the classifier, and that text is currently always this one synthetic string regardless of cause, a genuine stale-chunk engine-load failure (a 404'd chunk, matching the FR-051 pattern) can never be classified as stale by that regex today — it always falls through to ordinary filing, which is precisely the outcome User Story 3 exists to prevent. This feature therefore MUST change `loadEngine()` so that the original rejection (its `message` and, where the rejection itself wraps another error, its `cause`) is preserved and forwarded to the FR-051 classifier before any pattern match runs. The caller MAY still show the friendly synthetic string to the author in the `Stage: "error"` UI, but the classifier MUST see the original rejection text — only that text can ever match the dynamic-import-failure pattern.
- **FR-006**: A crash captured by any of FR-001 through FR-004 MUST be classifiable by kind (`render`, `onerror`, `rejection`) in the payload, so a maintainer reading the filed issue can tell which surface caught it. A fourth kind, `pre-mount` (group G, FR-060-FR-064), classifies a crash caught before any of FR-001-FR-004 could have installed — the client does not send it explicitly (FR-062's payload has no `kind` field); the server defaults an absent `kind` to `"pre-mount"` (FR-081).
- **FR-007**: Capturing a crash MUST NOT depend on any prior successful compile, validation run, or working-copy state — a crash before any of those exist (e.g., during identity-lite, before a working copy is instantiated) MUST still be capturable.
- **FR-008**: `warmExemplarSource().catch(() => {})` ([main.tsx:47](../../packages/studio/src/main.tsx#L47)) and any other deliberately self-swallowing `.catch()` in the codebase MUST continue to never reach the `unhandledrejection` handler — this feature does not change what already correctly self-swallows.

### B. Client self-containment — the P0

- **FR-010**: The crash-capture module (hashing, redaction, payload construction, POST) MUST be self-contained within the studio's main bundle. It MUST NOT contain a dynamic `import()`, and its own import graph MUST NOT reach `@keyboard-studio/engine`, directly or transitively.
- **FR-011**: `crypto.subtle.digest("SHA-256", ...)` MUST be called directly inside the crash module. `computeSha256Hex` ([packages/engine/src/codec/hash.ts:14](../../packages/engine/src/codec/hash.ts#L14)) MUST NOT be imported by it, despite being functionally identical — importing it would pull the crash module's fingerprinting dependency onto the exact package whose failure-to-load is one of this feature's target crash classes.
- **FR-012**: The crash module MUST NOT import `decisionLogStore.ts`, `workingCopyStore.ts`, or any other module whose own import graph reaches `@keyboard-studio/engine` as a value (E-4). Structural context sourced from those stores MUST be read by the *caller* (the ErrorBoundary, the `window.onerror` handler, the `unhandledrejection` handler) and passed into the crash module as plain data (group E).
- **FR-013**: A repository-level test MUST assert the crash module's reachable import graph contains zero references to `@keyboard-studio/engine`, mirroring the walking approach `api/bundle-safety.test.ts` already uses for the serverless functions. This test MUST be demonstrated failing against a version of the crash module that violates FR-010/FR-012 before it is trusted as a gate — an assertion that has never been seen red is not evidence.
- **FR-014**: The crash module MUST be reachable and functional even when `loadEngine()` ([useKeyboardArtifact.ts:45-61](../../packages/studio/src/hooks/useKeyboardArtifact.ts#L45)) has already failed for the current session — its own success or failure MUST have no bearing on whether a crash can be captured and reported.

### C. Client-side local fingerprint (session dedupe only — never authoritative)

**Revised in review cycle 2 (P0-1).** This group previously specified the client as the sole computer of the fingerprint used for server-side lookup and mutation. That design is rejected — see the fingerprint clarification above — in favor of server-side, authoritative computation (Group I, FR-081a-FR-081f). The client still computes a fingerprint, but strictly as a local cache key; it carries no trust and is never transmitted.

- **FR-020**: The client MUST compute a local fingerprint using the identical canonicalization algorithm specified for the server (FR-081a: crash kind + normalized message + top 3-5 stack frames as `function@modulePath` with line/column dropped and chunk-hash suffixes stripped), hashed via `crypto.subtle.digest("SHA-256", ...)` called directly inside the crash module (FR-011). This value is used exclusively as the key for the client's own per-session dedupe cache (FR-101, group K).
- **FR-021**: The client MUST NOT send any client-computed fingerprint, hash, or dedupe key to the server. The wire payload carries only the raw structured inputs the server needs to compute its own authoritative fingerprint: `kind`, `message` (raw, unnormalized), and `stackFrames[]` (function name, module path, line, column — FR-081, FR-081a). Sending only raw inputs — never a pre-computed hash — is what makes server-side canonicalization authoritative rather than merely advisory (P0-1): the server cannot be told what the "right" fingerprint is, only what happened.
- **FR-022**: Because the client-local and server-authoritative fingerprints are computed by the identical algorithm over identical logical inputs, they normally agree bit-for-bit — but nothing in this feature depends on that agreement holding. A stale client build, a modified client, or a hostile caller producing a different local value has no effect on the server's own computation, which never reads or trusts anything the client computed.
- **FR-023**: Client-local fingerprint computation MUST be async-safe — it is event-driven (a crash, not a keystroke), so it engages no debounce cycle and is not subject to decision D3 (group N).
- **FR-024**: Two occurrences of logically the same bug within one browser session MUST produce the same client-local fingerprint, so the session dedupe cache (FR-101) actually dedupes; this is a session-scoped guarantee only — cross-session/cross-build stability of the fingerprint that actually matters for GitHub-side dedupe is the server's responsibility (FR-081a-FR-081f), not the client's.

### D. Redaction

- **FR-030**: The payload builder MUST be an **allowlist**, not a denylist: it reads named primitives off approved sources and never spreads an `Attribution` or `IdentitySession` object wholesale. Adding a new field to the payload requires extending the typed builder explicitly, which is visible in code review; there is no object in the pipeline holding a name or email that a denylist could forget to strip.
- **FR-031**: The following MUST NEVER appear in a filed report, under any payload field: `Attribution.authorName`, `Attribution.authorEmail`, `Attribution.copyrightHolder` ([attribution.ts:12-38](../../packages/contracts/src/attribution.ts#L12)); every field of `GitHubIdentitySession` and `GoogleIdentitySession` ([identity.ts:21-56](../../packages/studio/src/lib/identity.ts#L21)) including the GitHub `login`/token and the Google `sub`/`email`/`name`/`picture`; and any raw OAuth profile field not already named above.
- **FR-032**: Redaction MUST run at capture-time construction of the payload, not as a strip-at-send step. A strip-at-send design implies the disallowed fields existed in some intermediate structure (a stored draft, the breadcrumb ring) reachable by a future, unrelated code path (e.g., a hypothetical "copy debug info" button) — building the allowlisted object directly means the disallowed fields are never held anywhere in the report's own data structure.
- **FR-032a** (upstream-parity finding, added in review cycle 2): The payload builder's own module MUST carry a header comment stating, in the vendoring-note style [github-pipeline.ts:9-24](../../utilities/oauth-backend/src/github-pipeline.ts#L9) already uses for its own documented divergence, that this module does the **deliberate opposite** of `buildCommitMessage` / `buildPrBody` ([github-pipeline.ts:128-154](../../utilities/oauth-backend/src/github-pipeline.ts#L128)) — those functions intentionally embed author identity as public attribution on a contribution the author chose to submit; this builder intentionally strips it from unsolicited crash telemetry the author did not choose to send. FR-091 already requires this discipline for the label-over-Search-API decision; this is the parallel requirement for the redaction/attribution asymmetry, so a future reader does not "fix" the contrast by making one path match the other.
- **FR-033**: The server MUST additionally scrub the incoming `message`, `stackFrames[]`, `body`, and `context` strings for secret-shaped substrings (`ghp_`, `gho_`, `github_pat_`, `sk-`, `AKIA`, `xox[bp]-`, generic ≥32-character hex/base64 runs) and email-shaped substrings before any GitHub write, as defence in depth — the client is the primary redaction boundary (FR-030-032), but the constraint that the client is responsible for identity redaction does not mean the server trusts it blindly.
- **FR-033a** (P1, added in review cycle 2): The server MUST additionally neutralize `@mention`-shaped substrings (`/@[a-zA-Z0-9](?:[a-zA-Z0-9-]{0,38})/g`) in `message`, `stackFrames[]`, `body`, and `context` before any GitHub write — e.g. by inserting a zero-width space after the `@` or wrapping the token in an inline code span — so a filed report cannot be used to spam-notify arbitrary repository collaborators or organizations by name. This runs in the same scrub pass as FR-033 and applies to the same fields.
- **FR-033b** (P1, added in review cycle 2): Markdown image syntax (`![...](...)`) and raw `<img>` tags in `body` and `context` MUST be neutralized before any GitHub write (e.g. stripped or converted to a plain-text link) — an unneutralized remote image is a tracking-pixel vector against anyone who later views the issue (a maintainer, not the reporter). This is a **mitigation**, not merely an accepted risk: the fields in question are markdown rendered directly by GitHub's issue viewer, and stripping image syntax is no more destructive to actionability than the existing secret/email/mention scrubs.
- **FR-034**: A test MUST assert identity absence directly — constructing a payload from a fixture working copy that has real `Attribution` and `IdentitySession` values populated, and asserting none of FR-031's field values appear anywhere in the serialized payload (not merely that the builder "didn't crash").
- **FR-035**: Keyboard content itself (the working copy's structural facts named in group E) is explicitly **not** redacted — it is public by the user's own ruling, and redacting it would contradict the feature's stated purpose ("we need enough references to handle the bug").
- **FR-036**: The pre-mount fallback path (group G) is exempt from the full redaction pipeline by necessity (no working copy, no identity session exists to read from at that point) but MUST still send only `{ message, stack, appVersion }` (FR-062, revised in review cycle 4 to include the build identifier — see the residual P1 fix there) — it cannot read fields it has no access to, and it MUST NOT be extended to read `localStorage`/`sessionStorage` identity data directly, which would reintroduce exactly the leak this feature exists to prevent.

### E. Structural context and breadcrumbs

- **FR-040**: A filed report MAY include, when available: keyboard id, the composed BCP47 tag(s), the current step id, a key count, an exemplar count, and the tail (a bounded number of most-recent entries) of the existing decision log.
- **FR-041**: A filed report MUST NOT include a full VirtualFS snapshot or any raw file content from the working copy — group D's structural-context list is exhaustive, not illustrative.
- **FR-042**: The decision-log tail MUST be obtained by the **caller** reading `useDecisionLogStore.getState()` (or equivalent) and passing the resulting entries into the crash module's payload builder as plain data — the crash module itself never imports the store (FR-012, E-4).
- **FR-043**: The system MUST maintain a fixed-size (~50 entries) circular breadcrumb buffer at module scope, in the same category as the existing `window.__ksE2E__` diagnostic hook ([e2eHook.ts](../../packages/studio/src/lib/e2eHook.ts)) — plumbing, not React state, not persisted.
- **FR-044**: The breadcrumb buffer MUST be installed once at bootstrap by wrapping `console.error` / `console.warn`: it MUST call the original function **and** push to the ring, never replace existing console behaviour.
- **FR-045**: The breadcrumb buffer SHOULD record, at minimum: hash-route changes, step completions, `Stage` transitions, OAuth callback entry, and locale changes — general UI/console breadcrumbs, distinct from and complementary to the decision-log tail (FR-040), which is domain-scoped to authoring decisions only. The two MUST NOT be conflated: the decision log does not cover generic navigation or console output, and the breadcrumb ring does not cover authoring decisions. **This is the only SHOULD among this spec's requirements, deliberately (P2, addressed in review cycle 2):** the five listed instrumentation points are scattered across call sites the crash module itself never touches (route handling, step views, `Stage` transitions, OAuth entry, the i18n locale switch), so wiring every one of them is calling-code work outside this module's own testable surface, not a property the crash-reporting feature can enforce by construction the way FR-031's allowlist can. A report missing one of these breadcrumbs is still fully actionable — kind, message, stack, structural context (group E), and the decision-log tail are all separately guaranteed at MUST strength — whereas holding this list to MUST would tie this feature's completion to auditing every present and future call site touching those five signals, which is disproportionate for instrumentation whose absence degrades debugging convenience, not correctness or safety.
- **FR-046**: Every field named in FR-040 MUST be optional in the payload and MUST be omitted, not fabricated as an empty placeholder, when unavailable (e.g., no working copy yet).
- **FR-047**: No context field introduced by this group may itself be, or contain, any field named in FR-031 — a breadcrumb line logging a console warning that happened to print an author's email would defeat FR-030's allowlist model at a different layer; breadcrumb entries carry only structural facts (step ids, route hashes, stage names), never arbitrary free-text values that could carry identity through unnoticed.

### F. Stale-chunk carve-out

- **FR-050**: A `vite:preloadError` event MUST call `event.preventDefault()` and route into this group's handling rather than the ordinary crash-filing path.
- **FR-051**: A raw `import()` failure (not routed through Vite's preload machinery — e.g., `loadEngine()`'s own catch) MUST be matched against the stale-chunk message pattern (`/failed to fetch dynamically imported module|error loading dynamically imported module|importing a module script failed|failed to load module script|unable to preload css/i`) before any filing affordance is offered. **The last two alternatives were added after a production report:** a missing chunk answered by the SPA catch-all rewrite surfaces in Chrome as a module-script MIME complaint, not as a fetch failure, so the original three matched nothing for the very case this group exists to handle; `unable to preload css` is Vite's preload-helper wording for the same class. This match MUST run against the **original rejection text preserved by FR-005a**, never against a synthetic wrapper message a caller constructs afterward — a wrapper string cannot be relied on to contain the original failure's wording, and (per P0-3) the current `loadEngine()` caller's wrapper demonstrably does not.
- **FR-052**: On a first detection within a session, the system MUST read a `sessionStorage` timestamp key (e.g. `ks.staleChunkReloadedAt`); if absent or older than a tunable window (default 60 seconds, named as a constant, not a magic number), it MUST set the timestamp and call `location.reload()` exactly once, and MUST NOT file a crash report for this occurrence.
- **FR-053**: If a reload already occurred within the window and the same failure class recurs, the system MUST NOT reload again — it MUST surface a plain retry notice and, only then, allow the failure to proceed to ordinary filing (US3-3, edge case "genuinely unreachable chunk").
- **FR-054**: This carve-out MUST NOT introduce a validation timer or engage decision D3's debounce cycle — the sessionStorage timestamp check is a one-shot comparison, not a debounce, and produces no diagnostic (group N).
- **FR-055**: The reload-window constant MUST be named and adjustable in one place, not inlined at each call site.

### G. Pre-mount crash path

- **FR-060**: `main.tsx`'s `mountApp()` and `mountCallbackScreen()` MUST be wrapped in a top-level try/catch that activates before `createRoot(...).render(...)` runs.
- **FR-061**: On catching a pre-mount failure, the system MUST reveal a static, dependency-free fallback element already present in `index.html` ([packages/studio/index.html](../../packages/studio/index.html)) — no React render, no i18n catalog lookup, plain English text only, since neither can be assumed to have loaded successfully.
- **FR-062** (revised in review cycle 4, residual P1): The pre-mount path MUST attempt a best-effort `fetch` POST of `{ message, stack, appVersion }`, with a short timeout, and MUST swallow any failure of that POST silently — nothing in this path may throw a second uncaught exception. **`appVersion` is added here in review cycle 4**, correcting an omission: SC-011 requires every path, including pre-mount, to carry a non-empty build identifier, and FR-114 already requires that identifier to be readable pre-mount as a compile-time constant — `{ message, stack }` alone left FR-062 contradicting both. `kind`, `stackFrames`, and `occurredAt` remain omitted; the server treats their absence per FR-081's pre-mount exception (defaulting `kind` to `"pre-mount"`), never as a 400 (P0-B).
- **FR-063**: The pre-mount payload MUST NOT attempt to read `localStorage`/`sessionStorage` identity or working-copy data directly (FR-036) — it sends only what it can read from the caught error object itself.
- **FR-064**: The pre-mount POST target MUST be the same crash-report endpoint as the ordinary path (group I) — this feature does not introduce a second server route for the degraded case, only a smaller payload shape.

### H. Send behavior, notice, and retraction

- **FR-070**: A captured crash MUST be sent automatically, with no confirmation dialog gating the send — decision 6 rules out a confirm-before-send UX entirely.
- **FR-071**: After sending, the system MUST show a non-blocking notice naming that a report was sent, with a link to the filed (or commented-on) issue.
- **FR-072**: The recovery screen (the ErrorBoundary's fallback, for a render-throw crash) MUST use `role="alert"` and MUST move focus to its heading on mount — this is a whole-page state change, not an incremental update, so it is handled per [docs/accessibility.md](../../docs/accessibility.md) rule 4's focus-management requirement, not by an `aria-live` region.
- **FR-073**: A crash captured by `window.onerror` or `unhandledrejection` **without** a React render throw (the app has not been torn down; the rest of the page still functions) MUST present its notice as a lighter, non-disruptive surface — an `aria-live="polite"` region that announces without stealing focus — distinct from FR-072's whole-page recovery screen, since the surrounding UI is still usable and stealing focus would be disruptive rather than helpful.
- **FR-074**: The notice MUST remain visible for exactly `CRASH_REPORT_UNDO_WINDOW_MS`, a named, adjustable constant defaulting to **30,000 (30 seconds)**, during which an "Undo" affordance is available — replacing the original "a few tens of seconds" wording (untestable as written; fixed in review cycle 2, P1). SC-013 ties a measurable outcome to this constant.
- **FR-074a** (P0-6, new in review cycle 10 — server-authoritative retraction target): The retraction endpoint MUST NOT read the issue number, action, or comment id from its request body. `POST /report/crash` MUST return a signed, expiring **capability token** alongside every successful report, and `POST /report/crash/retract` MUST accept that token as its **only** parameter and derive everything it acts on from the token's verified payload. **Why this is a P0 rather than hardening:** the retraction route is public and unauthenticated, issue numbers in `keyboard-studio/crash-reports` are sequential and publicly visible, and the `CRASH_REPORT_UNDO_WINDOW_MS` window (FR-074) is UI state in the client — so a body-supplied target let any anonymous caller close, or comment-delete from, an arbitrary crash report belonging to someone else, at no cost and with no time bound. This is the same defect class as the client-supplied fingerprint (P0-1) and takes the same fix: **remove the forgeable field** rather than validate it. Requirements on the token: HMAC-signed with key material **derived from `CRASH_REPORT_APP_PRIVATE_KEY`** (domain-separated; deliberately *not* a sixth environment variable, because a secret whose absence silently disables an authorization check must not join the manual prerequisites — the App key is already mandatory, so no "configured but unsigned" state exists); a bounded TTL, `CRASH_RETRACTION_TOKEN_TTL_MS`, defaulting to **120,000 (2 minutes)** — looser than the 30 s visible window so the server never becomes the reason a legitimate Undo fails, but the first server-side time bound this route has; **stateless** (FR-105 — the token is the record, no KV or issued-token table); verification **before** the installation-token mint and before any GitHub call, so forgeries cost nothing against the App's rate budget; and **one undifferentiated rejection**, `403 retraction_not_authorized`, for every failure reason, since a caller able to distinguish "bad signature" from "expired" learns whether it guessed the key. A replay inside the TTL is accepted as a residual: it is idempotent in effect and cannot reach any issue other than the one the token names.
- **FR-075**: Activating "Undo" on a report whose action was `"created"` MUST close the filed issue and add a comment marking it retracted by the reporter — true deletion is not available to an installation token (Clarifications) and MUST NOT be attempted or implied by the UI copy.
- **FR-076**: Activating "Undo" on a report whose action was `"commented"` MUST remove only the comment added this session, never touch the issue's open/closed state, and never touch any other comment on it.
- **FR-076a** (new in review cycle 10, implementation gap): The `200` response to `POST /report/crash` MUST carry the `commentId` of the comment that request added, when it added one. FR-076 requires Undo to remove *only this session's* comment, and the client cannot name that comment without being told its id. The id is carried inside FR-074a's capability token as well as in the response body, so the retraction target remains server-verified rather than client-asserted.
- **FR-077**: Once the notice's window elapses or it is dismissed, the "Undo" affordance MUST disappear, and the filed report MUST stand unchanged thereafter.
- **FR-078**: The send call itself MUST be fire-and-forget from the studio's perspective: a network failure, a 5xx, or a 503 from the server MUST NOT be surfaced to the author as an actionable error, and MUST NOT be retried in a loop (a retry loop would itself become the comment-flood scenario group K exists to prevent).

### I. Server route, schema, authoritative fingerprint computation, and the GitHub caller

- **FR-080**: A new route, `POST /report/crash`, MUST be added, rewritten in `vercel.json` to `/api/report/crash` following the existing pattern (`vercel.json`'s `rewrites` array, e.g. the `/submit/managed-pr` entry).
- **FR-081** (revised in review cycle 4, P0-B; originally revised in review cycle 2, P0-1): A new zod schema (`CrashReportBodySchema`) MUST validate: `kind` (enum `"render" | "onerror" | "rejection" | "pre-mount"`, FR-006, **optional**), `message` (raw, unnormalized, max 4096), `stackFrames` (array, max 20 entries, each `{ function: string (max 200), modulePath: string (max 300), line: number.int().nonnegative().optional(), column: number.int().nonnegative().optional() }`, **optional**), `stack` (raw, unparsed `Error.stack` text, max 8192, **optional** — accepted specifically so the pre-mount path, FR-062, can send it before any structured-frame-extraction machinery exists to run), `appVersion` (max 40, **optional**), `occurredAt` (ISO datetime, **optional**), and an optional `context` object (`browserUA` max 300, `os` max 100) — sizes mirroring the existing cap discipline in `ManagedPRBodySchema` ([managed-pr-schemas.ts:15-33](../../utilities/oauth-backend/src/managed-pr-schemas.ts#L15)). **`fingerprint` and `title` are deliberately removed from this schema, reversed from the original draft:** the server computes both (FR-081a-FR-081f for the fingerprint; FR-093a for the title) from the raw fields above, so no client-supplied value can influence which issue a report lands on or what it is titled. **Pre-mount exception (group G), corrected in review cycle 4 (P0-B):** `kind`, `stackFrames`, `appVersion`, and `occurredAt` MUST all be optional. The review-cycle-2 revision exempted `stackFrames`/`appVersion`/`occurredAt` but left `kind` required — since FR-062's pre-mount body has no `kind` field to supply, every pre-mount report failed schema validation with a 400, silently disabling the one crash class an ErrorBoundary structurally cannot catch (a regression the cycle-2 redesign introduced; cycle 1's schema had no `kind` field at all). **Fix:** when `kind` is absent, the server MUST default it to the distinct `"pre-mount"` classification (FR-006) before canonicalization runs. When `stackFrames` is absent, the server derives its best-effort equivalent by parsing the raw `stack` string's lines (FR-081a, FR-081f), so FR-081a's canonicalization has a single code path regardless of which capture surface produced the report. **Conditional validation (P2, new in review cycle 5):** making `stackFrames`/`stack`/`appVersion`/`occurredAt` unconditionally optional would let a malformed **post-mount** report validate with only `kind` and `message`, letting unrelated bugs that happen to share a generic message over-collide onto one fingerprint. The schema MUST therefore add a `.refine()` requiring at least one of `stackFrames` or `stack` to be present whenever `kind` is present and is not `"pre-mount"` — i.e. the pre-mount exemption applies only when `kind` is absent or explicitly `"pre-mount"`; every other `kind` MUST carry frame data.
- **FR-081a** (P0-1, new in review cycle 2): The server MUST canonicalize the fingerprint input as: `kind` (FR-006) + a normalized `message` (stack-trace addresses and quoted user-supplied substrings stripped) + the top 3-5 entries of `stackFrames`, each rendered as `function@modulePath` with `line`/`column` dropped (they shift on any rebuild independent of any logic change) and chunk-hash suffixes in `modulePath` canonicalized to a stable form (e.g. `main-DLGH1X0S.js` → `main.js`) before hashing, so a rebuild alone does not fork a new fingerprint for the same bug. This is the same algorithm the original (rejected) client-side design specified — only *where* it runs has changed. **Pre-mount case (P0-B, new in review cycle 4):** when `stackFrames` is absent (FR-081's pre-mount exception) but a raw `stack` string is present, the server MUST derive the equivalent top 3-5 frames from `stack` per the precise rule in FR-081f, then apply the identical `function@modulePath` rendering, line/column drop, and chunk-hash canonicalization as the structured case, so the two code paths converge on the same canonical shape before hashing. When neither `stackFrames` nor a parseable `stack` is present, the frame portion contributes nothing and the canonical string is `kind` + normalized `message` alone — with `kind` defaulted to `"pre-mount"` (FR-081, FR-006), this remains a stable, still-reasonably-collision-resistant fingerprint: two genuinely different pre-mount failures would need an identical error message to collide, which is the same low-entropy-input risk any fingerprinting scheme accepts when less input is available, not a new collision class this fallback introduces.
- **FR-081b**: The build identifier (commit SHA / app version, group L) MUST be **excluded** from the fingerprint's hash input and carried as a separate payload field instead — hashing it would fork a new issue on every deploy, defeating "one issue per bug." Carrying it outside the hash lets the server record "seen again in build X" on the existing issue without forking.
- **FR-081c**: The server MUST compute `sha256(canonicalizedInput)`, encode it as lowercase hex, and truncate to 12 characters for the dedupe label (`crash/fp-<hash12>`); the full digest MAY be retained internally but only the 12-character form is used for the label and the auditability comment (FR-092). No client-supplied fingerprint, hash, or dedupe key of any kind is read, validated, or trusted for this purpose (P0-1) — there is none in the schema (FR-081) to read.
- **FR-081d** (worked example, required for independent testability): Given
  ```
  kind = "render"
  message = "TypeError: Cannot read properties of undefined (reading 'label')"
  stackFrames = [
    { function: "KeyEditor",       modulePath: "assets/main-DLGH1X0S.js",   line: 142, column: 18 },
    { function: "renderWithHooks", modulePath: "assets/vendor-9f3ac21b.js", line: 3,   column: 4021 }
  ]
  ```
  canonicalization (FR-081a) proceeds in three steps: (1) **message normalization** strips the single quoted substring, yielding `TypeError: Cannot read properties of undefined (reading <redacted>)`; (2) **frame canonicalization** drops `line`/`column` from each frame and collapses the chunk-hash suffix in `modulePath` (the trailing `-[\w-]{8,12}` before `.js`) to `assets/main.js` and `assets/vendor.js` respectively, rendering each frame as `function@modulePath`; (3) the three pieces join, delimited, in the fixed order kind, message, frames. The exact joined string for this input is:
  ```
  render|TypeError: Cannot read properties of undefined (reading <redacted>)|KeyEditor@assets/main.js|renderWithHooks@assets/vendor.js
  ```
  The fingerprint is `sha256(...)` of that exact string, hex-encoded, first 12 characters. This spec deliberately does not assert a specific hex literal here — the three canonicalization steps above are specified precisely enough that an implementation's own test fixture computes and pins the digest once; inventing an unverified hash value in prose would be worse than none. A conformance test MUST assert the exact canonicalized string shown above for this exact input, and MUST assert the resulting hash is stable across a second input that differs only in `line`/`column`/chunk-hash-suffix, and differs (does not collide) across an input with a genuinely different `message` or `function` name.
- **FR-081e**: The server's fingerprint computation MUST be a pure function of its input (kind, normalized message, canonicalized frames) — no I/O, no reliance on request headers, no dependency on which repository or label currently exists — so it is unit-testable in isolation from the GitHub-calling parts of the pipeline.
- **FR-081f** (P1, new in review cycle 5 — raw-`stack` extraction rule, worked example, and stability, symmetric with FR-081d/FR-081a's structured path): The server MUST extract frames from a raw `stack` string as follows: (1) split on `\n`; (2) if the first line does not itself match the frame pattern below (V8 prepends the error's own message line; Firefox and Safari do not), discard it; (3) match each of the next 3-5 lines against `/^\s*(?:at\s+)?(?:(?<fn>[^\s@()]+)\s*[@(]\s*)?(?<path>[^\s():]+):(?<line>\d+):(?<col>\d+)\)?\s*$/`, tolerating both the V8 shape (`    at fn (path:line:col)`) and the Firefox/Safari shape (`fn@path:line:col`); (4) where `fn` did not capture (an anonymous frame), substitute the literal `<anonymous>`; (5) feed the resulting `{ function, modulePath: path, line, column }` tuples into the same canonicalization FR-081a already applies to structured `stackFrames` (drop `line`/`column`, strip the chunk-hash suffix from `modulePath`, render as `function@modulePath`). **Worked example (two browser shapes converging):** given the same underlying error, a V8-style raw stack
  ```
  TypeError: Cannot read properties of undefined (reading 'label')
      at KeyEditor (assets/main-DLGH1X0S.js:142:18)
      at renderWithHooks (assets/vendor-9f3ac21b.js:3:4021)
  ```
  and a Firefox/Safari-style raw stack for the identical failure
  ```
  KeyEditor@assets/main-DLGH1X0S.js:142:18
  renderWithHooks@assets/vendor-9f3ac21b.js:3:4021
  ```
  both extract the same two frames and canonicalize, after chunk-hash stripping, to the identical frame portion `KeyEditor@assets/main.js|renderWithHooks@assets/vendor.js` — matching FR-081d's own structured-path frame portion for the same underlying bug, which is the intended convergence. As with FR-081d, no specific hex digest is asserted in prose; a required conformance test MUST assert both raw-stack shapes above produce this exact frame portion (and, combined with the same `kind`/normalized `message`, the identical fingerprint), and MUST assert that a raw `stack` string whose frames genuinely differ (different function name or file) produces a different fingerprint — closing the gap where cross-browser stack-string variance could otherwise fork one pre-mount bug into two issues.
- **FR-082**: The schema module MUST NOT value-import any `@keyboard-studio/*` package (only `import type` is permitted, per the existing bundle-safety rule); any literal that would otherwise be imported from `packages/contracts` MUST be copied locally behind a compile-time drift guard, following the `GITHUB_OAUTH_CLIENTS` idiom ([schemas.ts:30](../../utilities/oauth-backend/src/schemas.ts#L30), [:136-157](../../utilities/oauth-backend/src/schemas.ts#L136)).
- **FR-083** (revised in review cycle 2, P0-2): The route MUST follow the existing four-way structural split, plus one new file this feature's separate App requires: a schema module, a pipeline module (`crash-report-pipeline.ts`) owning GitHub calls, fingerprint canonicalization (FR-081a), and pure helpers, a thin Vercel Web-fetch adapter (`api/report/crash.ts`, structurally mirroring `api/submit/managed-pr.ts`), a matching Fastify route registered in `server.ts` for local-dev parity, and a **new token minter** (`crash-report-installation-token.ts`, FR-085) — structurally identical to `installation-token.ts` but reading the separate `CRASH_REPORT_APP_*` env vars (Prerequisites), never shared with the managed-PR pipeline's minter.
- **FR-084**: **The third-GitHub-caller decision (resolved, per this spec):** the pipeline module MUST hand-write a minimal GitHub REST caller inside `oauth-backend` covering exactly the endpoints this feature needs — issue list-by-label, issue create, issue comment, issue reopen/label-patch — rather than attempting to extract a shared client. Full extraction is blocked by the same bundle-safety constraint that already prevents `packages/engine/src/output/github.ts` and `github-pipeline.ts` from merging (E-5); a third minimal, hand-documented caller is the smaller and more honest cost. The divergence MUST be documented in the new module's header comment in the same style `github-pipeline.ts:9-24` documents its own vendoring, naming explicitly that this is caller #3 and why it was not extracted.
- **FR-085** (revised in review cycle 2, P0-2): A new, dedicated token minter (`crash-report-installation-token.ts`) MUST provide `getCrashReportInstallationToken()`, mirroring the structure of `getInstallationToken` in `installation-token.ts` but reading `CRASH_REPORT_APP_ID` / `CRASH_REPORT_APP_PRIVATE_KEY` / `CRASH_REPORT_APP_INSTALLATION_ID` (Prerequisites #4) instead of `GITHUB_APP_ID` / `GITHUB_APP_PRIVATE_KEY` / `GITHUB_APP_INSTALLATION_ID`. **This reverses the original draft's "reuse `getInstallationToken` unchanged" decision.** The managed-PR pipeline's token minter and its three env vars MUST NOT be reused, read, or referenced by this feature's pipeline — the whole point of the separate App (Prerequisites, P0-2) is an independent credential and an independent rate budget, and sharing the minter would silently reintroduce the coupling the separate App exists to remove.
- **FR-086**: `"api/report/crash.ts"` MUST be added to `FUNCTION_ENTRIES` in [api/bundle-safety.test.ts:41-50](../../api/bundle-safety.test.ts#L41), so the bundle-safety walk covers the new function's reachable graph.
- **FR-087**: Response and error vocabulary MUST match the existing convention: `200 { issueUrl, issueNumber, action: "created" | "commented" | "reopened" }`; `400 invalid_request`; `429 rate_limited` (+ `Retry-After`); `502 submission_unavailable` / `upstream_error`; `503 reporting_not_configured` — identical to `github-pipeline.ts`'s `mapNonOk` vocabulary ([github-pipeline.ts:215-229](../../utilities/oauth-backend/src/github-pipeline.ts#L215)), so no new error taxonomy is introduced for a structurally identical failure class. `issueUrl` / `issueNumber` are runtime values read back from GitHub's own create/comment/reopen response, not literals in source — they do not engage the spec §18/§19 rule against citing issue numbers in shipped code (Governing documents).
- **FR-088**: A 401/403 from GitHub (misconfigured or not-yet-approved crash-reporting App installation, Prerequisites #3) MUST map to `502 submission_unavailable`, never revealing which credential or permission is at fault.
- **FR-089**: The target repository (`keyboard-studio/crash-reports`) MUST be a source constant, not derived from request input — a crash report can never redirect where it is filed.

### J. Dedupe and regression handling

- **FR-090**: Dedupe MUST be performed via the `crash/fp-<hash12>` **label** (the fingerprint computed server-side per FR-081a-FR-081c), looked up through `GET /repos/{owner}/{repo}/issues?labels=crash/fp-<hash>&state=all&per_page=5` — the ordinary REST issues endpoint, drawing on the crash-reporting App's own normal 5,000/hr budget (Prerequisites, P0-2).
- **FR-091**: Dedupe MUST NOT use `GET /search/issues` under any circumstance. A code comment at the lookup call site MUST state why (indexing lag of seconds to minutes; a 30 req/min limit shared across the whole installation), so a future contributor does not "optimize" this back to Search.
- **FR-092**: The fingerprint MUST additionally be embedded in the issue body as a trailing HTML comment (`<!-- crash-fingerprint: <hash> -->`) for human auditability — this is documentation, not the lookup mechanism; only the label is read for matching.
- **FR-093**: No match found → create a new issue carrying the `crash/fp-<hash12>` label, the generated title (FR-093a), and the fingerprint comment (FR-092), subject to the global creation cap (FR-106, group K).
- **FR-093a** (upstream-parity finding, new in review cycle 2 — the single most project-specific gap the parity review found): The generated issue title MUST be `bug(studio): <normalized message summary>`, following CLAUDE.md's `<prefix>(<area>): <description>` issue-title grammar. `<normalized message summary>` is derived from the FR-081a-canonicalized message, truncated to a reasonable title length (e.g. 72 characters, ellipsized). The title MUST NOT include the crash `kind`, the fingerprint, or the build id — those belong in the body only (FR-092, group L), keeping the title scannable in a repository issue list. **`bug` is used, not `auto`:** CLAUDE.md reserves `auto` for machine-generated *housekeeping* (dependency bumps, version bumps) with no defect content, and reserves `bug` for a reported defect. The filer here is a machine, but the *content* is a genuine defect report — an uncaught exception a real author hit — so `bug` is the correct classification of the content, even though `auto` would describe the mechanism. Because the schema no longer accepts a client-supplied `title` (FR-081), this is the only issue-title path — there is no client override to reconcile it with.
- **FR-094** (clarified in review cycle 4, P0-A): Match found, issue open → add a comment recording the new occurrence, subject to FR-102's comment cap; no new issue is created and **no state-change call is made at all** — an issue that is already open has no open/closed state left to change, so FR-095/FR-095a's reopen-and-label path never applies to this branch. Made explicit here because reopen is now itself a rate-limited action (FR-095a) and this branch's exemption from it should not be left implicit.
- **FR-095** (revised in review cycle 4, P0-A): Match found, issue closed → the reopen and `regression` label addition happen, bounded by FR-095a's cooldown rather than unconditionally, and a comment recording the regression is added when the reopen itself proceeds. **This revises the review-cycle-2 wording**, which required the reopen unconditionally on every hit. Review cycle 4 identified that wording as an unbounded regression-spam vector (P0-A): it exempted the reopen/label state-change from every flood-control layer — FR-102's comment cap governs comments only, and FR-106's creation cap gates FR-093 creates only — and a closed issue's own content (`message`, `stackFrames`, and the fingerprint itself, echoed in the body per FR-092) is public, so a caller who copies it verbatim can force repeated reopen calls at no cost. The fix bounds the reopen with a cooldown rather than exempting it; see FR-095a.
- **FR-095a** (revised in review cycle 4, P0-A; originally P1, new in review cycle 2): The reopen and `regression` label addition (FR-095) MUST happen **at most once per `CRASH_REPORT_REOPEN_COOLDOWN_MS` per fingerprint**, derived from the same stateless signals FR-102 already reads off the label-lookup response — the matched issue's `state` and `updated_at` — requiring no external store. Concretely: if the matched issue's state is CLOSED and its `updated_at` is **not** within `CRASH_REPORT_REOPEN_COOLDOWN_MS` of now, the reopen, label, and comment MUST proceed. If the matched issue's state is CLOSED but its `updated_at` **is** within that cooldown (a near-simultaneous duplicate racing an in-flight reopen, or a rapid resubmission before the window elapses), the reopen/label/comment call MUST be suppressed, and the response MUST use the same non-fatal shape a suppressed comment already uses (FR-104) — never an error the client acts on. **The guarantee this requirement preserves: the first regression hit after a close always reopens — the cooldown bounds churn, never the signal.** This reverses the review-cycle-2 wording, which read FR-102's comment cap as also exempting the reopen/label state-change from flood control entirely; that was the gap (P0-A). FR-102's own cap continues to govern comment writes only and does not, by itself, bound reopens.
- **FR-096**: A failure of the dedupe lookup itself (network error, 5xx) MUST fail **open** to issue creation, not closed — an occasional duplicate is preferable to a silently dropped report.
- **FR-097**: Two near-simultaneous first-occurrence requests for the same fingerprint MAY both proceed to create — this is an accepted, self-healing race, not something this feature adds distributed locking to prevent.
- **FR-098**: `429` responses from GitHub MUST be honoured exactly as `github-pipeline.ts` already does — surfaced as `429 rate_limited` with `Retry-After` taken from the response header (default 60s if absent/non-numeric).
- **FR-099**: The `crash/fp-*` and `regression` label vocabulary is a project-local ops convention scoped to `keyboard-studio/crash-reports` only. It is deliberately not modeled on keymanapp/keyman's flat label scheme and MUST NOT be assumed to apply to, or propagate into, `keyboard-studio/keyboards` or any upstream repository (upstream-parity finding, Assumptions).

### K. Flood control

- **FR-100** (revised in review cycle 2, P0-2): Flood control MUST compose **four independent layers**, three of which are code this feature ships and one of which is platform configuration: a client-side per-session cache (FR-101, code), a server-side comment cooldown (FR-102, code, extended by the reopen cooldown FR-095a — see below), a server-side global creation cap (FR-106, code), and a platform-level rate-limit rule on the route (Prerequisites #5, **configuration, not code**). None alone is sufficient — the client-side cache does nothing for a fresh tab or a different user hitting the same bug; the server-side comment cap does nothing to prevent the POST attempts themselves from a single crash-looping session, to bound distinct-fingerprint issue *creation*, or (before review cycle 4's P0-A fix, FR-095a) to bound *reopen* churn on a closed match; the global creation cap does nothing to prevent repeat comments or repeat reopens on one already-existing issue; and none of the three code-level layers bounds a distributed, low-and-slow burst from many source IPs as cheaply as the platform rule does before any request reaches application code at all.
- **FR-101 (client layer)**: The client MUST cache "already reported this fingerprint" in `sessionStorage`, keyed by fingerprint, so a crash loop within one session does not repeatedly POST for the same bug.
- **FR-102 (server comment-cap layer)**: The server MUST cap **comment writes** on a matched issue using **stateless** signals already present in the label-lookup response — the issue's own `comments` count and `updated_at` timestamp — requiring no external store (no KV, no Redis). The comment write MUST be skipped (while still returning `200` to the client) when the matched issue's comment count is at or above a tunable cap, **or** its `updated_at` falls within a tunable cooldown window. **This cap governs comment writes only.** The reopen/label state-change on a regression match (FR-095) is governed by its own, separate cooldown — FR-095a — not by this cap; review cycle 2's wording read FR-095a as exempting the reopen from flood control entirely, which review cycle 4 corrected (P0-A).
- **FR-103** (extended in review cycle 4, P0-A): The comment cap and cooldown, and the reopen cooldown, MUST be named, adjustable constants — e.g. `CRASH_REPORT_COMMENT_CAP` (default 20), `CRASH_REPORT_COMMENT_COOLDOWN_MS` (default 10 minutes), and `CRASH_REPORT_REOPEN_COOLDOWN_MS` (default 10 minutes, FR-095a) — not inlined magic numbers, mirroring how `AUTOSAVE_DEBOUNCE_MS` / `CLOUD_SYNC_DEBOUNCE_MS` are named constants elsewhere in the codebase.
- **FR-104**: Skipping a comment write under FR-102 MUST still return the normal `200 { issueUrl, issueNumber, action: "commented" }` shape to the client — the client has no way to distinguish "commented" from "skipped, already at cap," and does not need to; the notice (group H) reads the same either way.
- **FR-105**: No distributed rate-limiting infrastructure (a shared KV store, Redis, a token-bucket service) is introduced for v1 — the code-level layers rely on state that already exists (`sessionStorage`, the matched issue's own metadata, the target repository's own recent issue-creation history for FR-106) rather than new infrastructure; the platform-level layer (FR-100, Prerequisites #5) is Vercel's own managed feature, not infrastructure this feature builds or operates.
- **FR-106** (P0-2, new in review cycle 2 — bounded global creation cap; **query amended in review cycle 10, P0-5**): Before creating a new issue (FR-093 only — this does not apply to the comment/reopen paths, which are already bounded by FR-102/FR-095a), the server MUST query recent issue-creation volume in `keyboard-studio/crash-reports` via the same REST issues endpoint (`GET /repos/{owner}/{repo}/issues?state=all&since=<now-CRASH_REPORT_GLOBAL_CREATE_WINDOW_MS>&sort=created&direction=desc&per_page=100&page=<n>`, no new infrastructure — this is the same stateless, GitHub-derived-state pattern FR-102 already uses) and skip creation when the count of issues created within that window is at or above `CRASH_REPORT_GLOBAL_CREATE_CAP` (named, adjustable constants; suggested defaults `CRASH_REPORT_GLOBAL_CREATE_WINDOW_MS` = 10 minutes, `CRASH_REPORT_GLOBAL_CREATE_CAP` = 200).

  **The probe MUST paginate (P0-5, review cycle 10).** The review-cycle-2 wording specified a single request at `per_page=100` against a cap of 200. GitHub caps `per_page` at 100, so that request can observe at most 100 creations and `count >= 200` is unsatisfiable arithmetic — this cap, described in this same requirement as the last line of defence, could never engage in production. Unit tests did not catch it because a stub `fetch` ignores `per_page` and returns whatever fixture size it is handed, which is a page no real API could produce. The corrected form reads up to `CRASH_REPORT_CREATE_PROBE_MAX_PAGES` pages, **derived** as `ceil(CRASH_REPORT_GLOBAL_CREATE_CAP / CRASH_REPORT_CREATE_PROBE_PER_PAGE)` rather than chosen, so raising the cap cannot silently reintroduce the gap; and it stops early on either a short page or a page contributing no in-window creations, which keeps a healthy tracker at exactly one request and spends extra requests only during an actual flood. `sort=created&direction=desc` is now explicit rather than defaulted, because that early exit depends on it: `since=` filters on *updated* time, so only a pinned created-descending order guarantees old-but-recently-commented issues sort behind every in-window creation instead of interleaving. Any test stub for this probe MUST honour `per_page` and `page` — a stub that does not is the mechanism by which this defect passed nine review cycles. A skipped creation MUST be surfaced as `429 rate_limited` with a `Retry-After` computed from the window — consistent with FR-078's fire-and-forget contract, the client never surfaces this as an actionable error. **Named residual risk and owner:** this cap, plus the Vercel Firewall per-IP rule (Prerequisites #5), bounds creation-flood cost without new infrastructure, but a sufficiently distributed attacker (many IPs, staying under both the per-IP threshold and this window-based cap) could still approach the crash-reporting App's own 5,000/hr ceiling before GitHub's own 429s throttle further calls. Because the crash-reporting App is separate from the managed-PR App (P0-2), that ceiling is this feature's own to exhaust, not a shared one — the residual risk is contained to this feature's own tracker filling with noise, not a cross-feature denial of service. Owner: the Engine team (spec §12), who can disable the route entirely and immediately by unsetting any of the `CRASH_REPORT_APP_*` env vars (Prerequisites), which the server already treats as "not configured" (503) with no deploy required.

### L. Build metadata

- **FR-110**: A Vite `define` MUST be added to `packages/studio/vite.config.ts` that surfaces the build's commit SHA at runtime, sourced from Vercel's `VERCEL_GIT_COMMIT_SHA` build environment variable, with a fallback (e.g. `"dev"`) for local/non-Vercel builds where that variable is absent.
- **FR-111**: The resulting identifier MUST be accessible as a compile-time constant (e.g. `__KS_COMMIT_SHA__`), typed via an ambient declaration, not read at runtime through `import.meta.env` alone — it must be present even in a pre-mount crash, before any env-reading module has necessarily executed.
- **FR-112**: The crash payload's `appVersion` field MUST combine the existing static `package.json` version with the short commit SHA (e.g. `0.1.0+<sha7>`), so both the release line and the exact deployed commit are visible in a filed issue without a second lookup.
- **FR-113**: This is on the critical path, not deferrable: no crash report ships without a build identifier — a report with no way to tell which deploy produced it is not actionable, which is the standard the whole feature is held to.
- **FR-114**: The pre-mount fallback (group G) MUST still be able to read the build identifier, since it is a compile-time constant rather than something computed at runtime from a module that might not have loaded.

### M. Accessibility and i18n

- **FR-120**: The ErrorBoundary's fallback screen MUST use `role="alert"` and move focus to its own heading on mount (FR-072), per [docs/accessibility.md](../../docs/accessibility.md) rule 4.
- **FR-121**: The lighter notice for a non-render-throw capture (FR-073) MUST use `aria-live="polite"` and MUST NOT move focus.
- **FR-122**: Every author-facing string this feature introduces MUST go through the message catalog under a new id following the `area.segment` grammar ([specs/046-i18n-localization/contracts/catalog-format.md](../046-i18n-localization/contracts/catalog-format.md)). At minimum: `crash.report.title`, `crash.report.sent.notice`, `crash.report.issue.link`, `crash.report.undo.button`, `crash.report.undo.confirmed`, `crash.report.retry.notice` (stale-chunk unreachable case).
- **FR-123**: The pre-mount fallback (group G) is the one deliberate exception: it MUST NOT go through the message catalog, since no locale has necessarily loaded at that point — its text is plain, hard-coded English, baked into `index.html`.
- **FR-124**: The recovery screen and the notice MUST both pass the project's existing automated accessibility scan (`expectNoSeriousAxeViolations` or equivalent) with zero new serious/critical violations.
- **FR-125**: Every interactive element on the recovery screen and notice (the issue link, the "Undo" button, any retry affordance) MUST be a real, keyboard-operable control — no click-only `div`.
- **FR-126**: No id introduced by this feature may repurpose an existing message id (spec 046: an id is a permanent handle) — every id in FR-122 is new.
- **FR-127**: Target-locale catalogs MUST not be left claiming a translation for an id this feature does not actually introduce, and the i18n lint gates (`i18n-catalog-lint`, `content-i18n-lint`) MUST pass with the new ids present.

### N. Non-regression

- **FR-130**: This feature MUST add no new validation timer. The single 300 ms debounce cycle (decision D3) remains the only validation cadence in the studio; the stale-chunk reload check (FR-052) is a one-shot `sessionStorage` comparison, not a debounce, and produces no diagnostic — the same reasoning CLAUDE.md already applies to `AUTOSAVE_DEBOUNCE_MS` / `CLOUD_SYNC_DEBOUNCE_MS`.
- **FR-131**: The `/api` bundle-safety invariant MUST hold for the new route: `api/bundle-safety.test.ts`'s "imports no workspace package as a value" assertion MUST pass with `api/report/crash.ts` added to `FUNCTION_ENTRIES` (FR-086).
- **FR-132**: A new, analogous test MUST assert the studio-side crash module's import graph never reaches `@keyboard-studio/engine` (FR-013) — this is a **new** test file, not an extension of `api/bundle-safety.test.ts`, since it covers the studio workspace bundle rather than the serverless functions.
- **FR-133**: This feature MUST NOT write anything into the emitted keyboard package, the downloaded archive, or any submitted pull request — crash telemetry is entirely out-of-band from the authoring output.
- **FR-134**: This feature MUST NOT change the working-copy spine, the decision record's append-only model, or its capture-boundary semantics — it only *reads* the decision log tail (FR-042), never appends to it.
- **FR-135**: Existing tests asserting today's "no ErrorBoundary" / "blank page on crash" behaviour (if any exist as incidental assertions rather than explicit tests) MUST be updated to reflect the new recovery behaviour, not left contradicting it.
- **FR-136**: The new server route MUST be covered by the same category of test the managed-PR route already has: a handler-level test with an injected fetch stub (no real network, no real GitHub token) exercising create / comment / reopen / rate-limit / not-configured paths.

## Key Entities

- **CrashReport (client)**: The redacted, allowlisted payload built at capture time — kind, raw message, raw stack frames, build identifier, optional structural context (FR-040), optional breadcrumbs. Carries no fingerprint field to the server (revised in review cycle 2, P0-1) — only the raw inputs the server needs to compute its own. Never holds an `Attribution` or `IdentitySession` object, only named primitives.
- **CrashReportBody (wire schema)**: The zod-validated shape the server accepts — `kind`, `message`, `stackFrames[]`, `stack`, `appVersion`, `occurredAt`, optional `context`, with `kind`/`stackFrames`/`appVersion`/`occurredAt` all optional (FR-081, revised in review cycle 2: `fingerprint` and `title` removed; `kind`/`message`/`stackFrames[]` added, so the server — not the client — computes both; revised again in review cycle 4, P0-B: `kind` made optional, defaulting to `"pre-mount"`, and a raw `stack` field added, so the pre-mount path's smaller body no longer 400s). Lives in `oauth-backend`, value-import-free of any `@keyboard-studio/*` package.
- **Fingerprint (server-authoritative)**: A 12-hex-character digest of a canonicalized error signature (kind + normalized message + top stack frames, chunk hashes and line/column stripped), computed **server-side** from the client's raw `kind`/`message`/`stackFrames[]` (FR-081a-FR-081c). Stable across rebuilds of the same bug; distinct across genuinely different bugs; never read from a client-supplied value.
- **Client-local fingerprint**: A same-algorithm digest computed client-side, used exclusively as the client's own per-session dedupe cache key (group C, group K). Never transmitted to the server; carries no trust; the server's fingerprint is authoritative regardless of whether the two agree.
- **Breadcrumb ring buffer**: A fixed-size (~50), module-scope, non-persisted circular buffer of UI/console events, wrapping `console.error`/`console.warn` without replacing them. Distinct from, and complementary to, the decision-log tail.
- **Decision-log tail**: A bounded read of the existing append-only decision record (`decisionLogStore.ts`), supplied to the crash module as plain data by the caller — never imported by the crash module itself (FR-012).
- **CrashIssue (server-side)**: The GitHub issue identified by the `crash/fp-<hash12>` label in `keyboard-studio/crash-reports`, titled `bug(studio): <normalized message summary>` (FR-093a) — created on first occurrence, commented on repeat (subject to the comment cap, FR-102), reopened with `regression` on a closed match at most once per `CRASH_REPORT_REOPEN_COOLDOWN_MS` (FR-095a, revised in review cycle 4, P0-A — no longer unconditional). Its label vocabulary is project-local ops convention (FR-099), not an upstream scheme.
- **Crash-reporting GitHub App**: A second, dedicated App installation (P0-2) — distinct from the managed-PR pipeline's App — installed only on `keyboard-studio/crash-reports`, granted only `issues:write`, with its own credential set (`CRASH_REPORT_APP_ID` / `CRASH_REPORT_APP_PRIVATE_KEY` / `CRASH_REPORT_APP_INSTALLATION_ID`) and its own independent 5,000/hr REST budget.
- **Flood-control state**: Derived, not stored — the client's `sessionStorage` fingerprint cache, the server's read of the matched issue's own `comments` count and `updated_at` (comment cap), and the server's read of recent issue-creation volume in the target repository (global creation cap, FR-106). No new persistent store is introduced; per-IP throttling is a platform (Vercel Firewall) configuration, not application state.
- **Build identifier**: A compile-time constant (`__KS_COMMIT_SHA__`, sourced from `VERCEL_GIT_COMMIT_SHA`) combined with `package.json`'s version, present even before any runtime module has executed.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Every render-throw, `window.onerror` capture, and unhandled-rejection capture — excluding the stale-chunk and pre-mount carve-outs — results in exactly one filed-or-commented GitHub issue, asserted against a stub GitHub API across the full crash-surface test suite.
- **SC-002**: Across 100 simulated repeat occurrences of the same fingerprint against an open matching issue, zero additional issues are created; all become comments on the one existing issue.
- **SC-003**: A stale-chunk failure followed by a successful reload results in zero filed reports; a stale-chunk failure that recurs after the reload window has already been used results in exactly one filed report.
- **SC-004** (trimmed to an outcome statement, P2): A crash occurring after `loadEngine()` has already failed for the session is still captured, fingerprinted, and filed — the reporter's own code never depends on the module whose failure it may be reporting. The mechanical guarantee is the gating import-graph test (FR-013/FR-132), which is demonstrated failing against a version of the module that violates the constraint before being trusted as green.
- **SC-005** (trimmed to an outcome statement, P2): An author with a fully populated identity — GitHub login, Google profile, attribution fields — can crash and have a report filed without a maintainer reading it ever learning who they are. Verified by asserting field-value absence (`authorName`, `authorEmail`, `copyrightHolder`, GitHub `login`/token, Google `sub`/`email`/`name`/`picture`) directly against a payload serialized from a fixture carrying real values for all of them (FR-034), not inferred from the builder's type shape.
- **SC-006**: A simulated crash loop of 100 identical occurrences within one session results in at most 1 client-initiated POST beyond the first (the session cache stops the rest); a simulated crash loop from 25 distinct sessions against the same fingerprint results in at most `CRASH_REPORT_COMMENT_CAP` comments on the matched issue.
- **SC-007**: A pre-mount crash, simulated by forcing a throw before `createRoot` runs, results in the static `index.html` fallback rendering and a best-effort POST being attempted, with no second uncaught exception surfacing regardless of whether that POST succeeds.
- **SC-008**: The ErrorBoundary's recovery screen reports zero new serious/critical automated-accessibility violations, uses `role="alert"`, and moves focus to its heading on mount; the lighter non-render notice uses `aria-live="polite"` and never steals focus.
- **SC-009**: Every string this feature introduces resolves through the message catalog under a new id (FR-122), and the i18n lint gates pass with zero orphaned or repurposed ids.
- **SC-010**: `pnpm crew-lint`, the bundle-safety test (with `api/report/crash.ts` added to `FUNCTION_ENTRIES`), and the new studio-side engine-reachability test all pass on the feature branch.
- **SC-011**: No filed issue, across the full test suite, ever carries a build identifier of `undefined` or an empty string — every path that can file a report (including the pre-mount path) carries one.
- **SC-012**: Retracting a `"created"` report closes the issue and adds a retraction comment; retracting a `"commented"` report removes only that session's comment; neither path attempts a GitHub delete call.
- **SC-012a** (P0-6, new in review cycle 10, ties FR-074a): `POST /report/crash/retract` is asserted to make **no GitHub call at all** for each of: a body naming an issue with no capability token (`400`), a syntactically malformed token, a token signed with a different key, a token whose payload was re-encoded to name a different issue, and a token presented past `CRASH_RETRACTION_TOKEN_TTL_MS` — each returning `403 retraction_not_authorized` with an identical body. A round-trip case asserts that the token `POST /report/crash` issues is accepted by the retract route and acts on the issue and comment the token names, not any named alongside it.
- **SC-013** (P1, new in review cycle 2, ties FR-074): The "Undo" affordance is present for exactly `CRASH_REPORT_UNDO_WINDOW_MS` (30,000 ms) after the notice appears and is asserted absent in a fake-timer test immediately after that window elapses — replacing the untestable "a few tens of seconds" wording.
- **SC-014** (P0-1, new in review cycle 2): Two requests carrying identical `kind`/`message`/`stackFrames[]` but a forged, mismatched value in any field the original design would have trusted as a fingerprint (now removed from the schema, FR-081) produce the same server-computed fingerprint and land on the same issue — demonstrating that no caller-supplied value can redirect a report to an issue its own content does not hash to (P0-1). A worked-example fixture (FR-081d) is asserted end-to-end: raw input → canonicalized string → stable hash.
- **SC-015** (P0-3, new in review cycle 2): Given a `loadEngine()` rejection whose message matches the stale-chunk pattern, a test asserts that message — not the synthetic `"Engine failed to load..."` string — is what reaches the FR-051 classifier, and that the carve-out fires. A companion test asserts a `loadEngine()` rejection that does **not** match the pattern still reaches ordinary filing, so FR-005a's fix does not over-suppress genuinely different engine failures.
- **SC-016** (P0-2, new in review cycle 2; **stub tightened in review cycle 10, P0-5**): A simulated burst of 50 distinct fingerprints within `CRASH_REPORT_GLOBAL_CREATE_WINDOW_MS` against a stub GitHub API that reports `CRASH_REPORT_GLOBAL_CREATE_CAP` issues already created in that window results in zero further issue-creation calls being attempted — the global cap is checked, and skipped creations map to `429 rate_limited`. The stub MUST page its response by the request's own `per_page` and `page` parameters, and the probe MUST be asserted to request the second page: with an unpaged stub this criterion passes against a probe that cannot fire in production at all.
- **SC-017** (P0-A, new in review cycle 4): A simulated burst of 50 requests carrying a closed issue's own public content (message, stack frames, fingerprint) results in **exactly one** reopen-plus-`regression`-label call within `CRASH_REPORT_REOPEN_COOLDOWN_MS`, not 50 — while a single request sent just after that issue was closed (outside any cooldown) always reopens it, demonstrating the preserved guarantee that the first regression hit after a close is never dropped.
- **SC-018** (P0-B, new in review cycle 4): A payload shaped exactly as FR-062 sends it — `{ message, stack, appVersion }`, no `kind`, no `stackFrames`, no `occurredAt` — validates against `CrashReportBodySchema` and results in a filed issue classified `kind: "pre-mount"`, not a `400 invalid_request`.
- **SC-019** (P1, new in review cycle 5, ties FR-081f): Two raw `stack` strings in the V8 shape and the Firefox/Safari shape, both describing the same underlying error (per FR-081f's worked example), canonicalize to the identical frame portion and produce the identical fingerprint; a raw `stack` string whose frames are genuinely different produces a different fingerprint — no two genuine pre-mount occurrences of the same bug fork into separate issues merely because they were thrown in different browsers.
- **SC-020** (P2, new in review cycle 5, ties FR-081): A post-mount request (`kind` other than `"pre-mount"`) carrying neither `stackFrames` nor `stack` is rejected `400 invalid_request` by the schema's `.refine()` (FR-081); the identical omission on a `kind: "pre-mount"` (or `kind`-absent) request validates normally.

## Assumptions

- This feature uses a **second, dedicated GitHub App** — never the managed-PR pipeline's App — installed only on `keyboard-studio/crash-reports` with only `issues:write` (Prerequisites, P0-2). Revises the cycle-1 assumption that the same App and credential set would be reused; that design would have let abuse of this public endpoint exhaust the installation budget the managed-PR submit path depends on.
- `keyboard-studio/crash-reports` is created, the new App is installed-on it, and the Vercel Firewall rate-limit rule (Prerequisites #5) is in place by the time this feature ships to production; until then, the route degrades to the existing 401/403/503 vocabulary rather than a distinct failure mode (Prerequisites).
- `keyboard-studio/crash-reports` sits entirely outside the staging-to-promotion model [github-pipeline.ts](../../utilities/oauth-backend/src/github-pipeline.ts) implements for `keyboard-studio/keyboards` (fork/branch/PR aimed at eventual upstream merge, per that file's `UPSTREAM_OWNER`/`UPSTREAM_REPO` staging comment). It is ops telemetry with no upstream analog — its issues are never promoted, merged, or forwarded anywhere.
- The `crash/fp-*` and `regression` label vocabulary (Group J) is a project-local ops convention for this one dedicated repository. It deliberately does not mirror keymanapp/keyman's flat label scheme and MUST NOT be assumed to propagate to `keyboard-studio/keyboards` or any upstream repository.
- The "short undo/delete window" (decision 6) is implemented as retract-via-close-and-comment, not true deletion, because GitHub's issue-deletion mutation is not available to an installation token; this is a definitive technical constraint, not an open design choice.
- The notice/undo window (FR-074) is fixed at `CRASH_REPORT_UNDO_WINDOW_MS` = 30,000 ms by this spec (revised in review cycle 2 from the original untestable "a few tens of seconds" wording); no upstream source dictated this exact value, but a named constant with a concrete default is required so SC-013 is testable.
- `decisionLogStore.ts`'s existing static dependency on `@keyboard-studio/engine` (E-4) is not something this feature fixes — it is worked around, at the call site, by passing plain data into the crash module rather than by refactoring the store's own imports. Removing that dependency, if ever desired, is a separate, unscoped change.
- The roughly 90 other studio files with a static value dependency on `@keyboard-studio/engine` mean the package is very likely already part of the main bundle's static dependency graph today, independent of this feature. This spec does not depend on that being true or false — FR-010/FR-012's requirement is about the crash module's *own* file-level import statements, verified by static analysis, regardless of how Rollup ultimately chunks the built output.
- No opt-out setting ("don't report my crashes") is introduced in v1 — decision 6 establishes auto-send as the default with no consent gate, and no probe or user decision asked for a persistent opt-out; if one is wanted later, it is a follow-up feature.
- No new distributed rate-limiting *infrastructure* is introduced; the code-level flood-control layers (group K: FR-101, FR-102, FR-106) rely on state that already exists (`sessionStorage`, the target repository's own issue metadata). Per-IP rate limiting is provided by the platform (Vercel Firewall, Prerequisites #5) rather than by application code.

## Out of Scope

- **True issue deletion.** Not available to an installation token; "Undo" retracts (closes + comments / removes a comment), it never deletes.
- **A persistent, cross-session client-side crash history or opt-out setting.** The session-scoped fingerprint cache (FR-101) is not a durable log, and no settings UI to disable reporting is introduced.
- **Distributed rate limiting or any new external store** (KV, Redis, Postgres). All code-level flood-control layers use state that already exists (group K); per-IP throttling is delegated to the Vercel Firewall platform feature (Prerequisites #5) rather than built.
- **Extracting a shared GitHub REST client package.** Blocked by bundle safety (E-5); this feature hand-writes a third minimal caller instead (FR-084), and does not attempt the extraction other callers have already been documented as unable to complete.
- **Retrying a failed send.** The client send is fire-and-forget (FR-078); no retry-with-backoff logic is introduced, since a retry loop is itself a flood-control hazard.
- **Changing what the emitted keyboard package, archive, or managed-PR body contains.** Crash telemetry is entirely out-of-band (FR-133).
- **Removing `decisionLogStore.ts`'s existing dependency on `@keyboard-studio/engine`.** Worked around (Assumptions), not fixed, by this feature.
- **Sentry, Bugsnag, or any third-party error-monitoring SDK.** This feature is a self-hosted, GitHub-issue-based reporter by design; adopting a vendor SDK is a different feature with a different governance question (a new outbound dependency, its own data-handling terms) not addressed here.
- **Multi-repository routing for crash reports.** All reports target one fixed repository (FR-089); per-keyboard or per-team routing is not in scope.
