# Contract — `flowQuestions` Tier B catalog

Extends spec 046's Tier B catalog contract (there is no standalone Tier B contracts doc there — the contract lives in `contentI18n.ts` + `utilities/i18n-content-extract/extract.ts`'s D8-decided field allowlist) with a fourth catalog type, `flowQuestions`, alongside `patterns`/`adaptationQuestions`/`criteria`.

## Catalog file

- **Location**: `content/i18n/{locale}/flowQuestions.json`.
- **Format**: flat JSON, `{ "<key>": "<text>" }` — identical shape to the other three Tier B catalogs. No nesting, no metadata.
- **Source (`en`)**: generated by `utilities/i18n-content-extract`'s `extractFlowQuestionStrings()`. Never hand-authored — regenerate, don't edit.
- **Target (`<lang>`)**: hand-authored ahead of the live Crowdin round-trip for the first non-English locale (`fr`), same precedent as T029/T030's `criteria.fr.json`; Crowdin owns it once the Tier B mapping's live round-trip is active for this catalog.

## Catalog key namespace

`content.flowQuestion.<questionId>.<field>`

- **`<questionId>`**: the `FlowQuestion.id` value verbatim — already unique across every live registry (enforced by `registry.test.ts`), so no phase prefix or slugification is needed (flow-question ids are already valid identifier-safe strings, unlike pattern/criterion ids which may contain literal dots).
- **`<field>`**: one of `prompt`, `label`, `body`, `help_text`, or `option.<optionValue>.label` for each entry in `FlowQuestion.options`.
- **Examples**: `content.flowQuestion.il_language_english.prompt`, `content.flowQuestion.il_language_english.help_text`, `content.flowQuestion.track_choice.option.copy.label`.

## Extraction rules (control-field exclusion, D8 discipline)

Only fields with a confirmed render site in `QuestionField.tsx` are extracted:

| Extracted | Render site |
|---|---|
| `prompt` | `QuestionField.tsx:764` (`labelText = question.prompt ?? question.label ?? question.id`), `QuestionField.tsx:730` (Notice fallback chain) |
| `label` | `QuestionField.tsx:764` (`??` fallback) |
| `body` | `QuestionField.tsx:730` (Notice fallback chain) |
| `help_text` | `QuestionField.tsx:789` |
| `options[].label` | option-rendering fields (radio/select/multi_select controls) |

Never extracted: `id`, `type`, `required`, `options_source`, `next`, `engine_resolved`, `advisory`, `options[].value`, `options[].note` — control data or fields with no confirmed render site.

Scope: only questions registered in a **live** phase sub-registry (`phaseARegistry`/`phaseBRegistry`/`phaseFRegistry`/`phaseGRegistry`) are extracted. `registry.reserve.ts`'s demoted modules are excluded — no live flow renders them, so there is nothing for a translator to usefully translate.

## Resolution / fallback contract

Identical to the existing three catalogs (`resolveContentString`, `packages/studio/src/lib/contentI18n.ts:109-121`): active-locale catalog lookup → English value already in hand → never blank, never the raw key. English never triggers a catalog fetch — `QuestionField.tsx` already holds the English string on the `FlowQuestion` object itself.

## What stays untranslated

The **answer values** a user types in response to these questions (a language's autonym, its English name, its BCP47 code, free-text entries, etc.) are user data, not content-i18n copy, and are never read by this catalog or the extractor. Only the static question prompt/label/body/help_text/option-label copy is in scope.
