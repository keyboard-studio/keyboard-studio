LDML 46 vs the current TR35 (CLDR 49), and what Keyman does with each

The format barely moved between 46 and 49, and no touch schema changed. Keyman does not ignore what it doesn't know: any 47+ feature fails the build. Keyman compiles LDML into KMX+, a binary block inside a .kmx, and its runtimes read only part of that block. Touch is the big gap, as you expected, but the gap is in Keyman, not in the LDML version. KMX+ is also where Keyman plans to close it.

Unchanged from 46 to 49: every other element and attribute. That covers keys/key (width, gap, longPress, multiTap, flickId, layerId, stretch), flicks, forms/scanCodes, layers/layer/row, variables, transforms/transformGroup/transform/reorder, displays, import, settings, locales.
The one fixed value that moves is version/@cldrVersion ("46" → "49"). It is optional, so the export leaves it out.
Not a 46 to 49 change: $[N:set]. TR35 prose says $[1:variable] is "(Where '1' is any numbered capture group from 1 to 9)" in both CLDR 46.1 and CLDR 49. The CLDR 49 transform-to grammar allows only mapped-set ::= '$[1:' var-id ']', and the $[1:…] set format may only be used where there is exactly one capture group with a set variable on the from= match string. A profile-49 export must not emit $[N:set] with N > 1; set mappings outside group 1 are expanded in both profiles.
The 47, 48 and 49 attributions above come from the release notes and the DTD diff. They were not re-verified against tr35-modifications.html; the 2026-11-01 TR35 reread checked only presence in 46.1 versus 49.

Does Keyman fail, or use what it understands?

It fails. Keyman validates the whole file against its CLDR-46 JSON schema before compiling. The schema allows conformsTo 45 or 46 only and rejects unknown attributes on 30 elements, including info and keyboard3. One violation stops the build, and no .kmx or .kvk is written. Only the first violation is reported.

Keyman is also stricter than TR35 within 46

  • A set mapping must be capture group 1 and fill the whole to ($[1:set]). TR35 prose mentions groups 1 to 9 in both 46.1 and 49, but the CLDR 49 grammar allows only $[1:set]. On $[N:set] with N > 1, Keyman fails the build (Error_IllegalTransformToUset); the upstream fix, draft PR #16870, is unmerged. This is a Keyman-side fact, not a difference between profiles.
  • Only one set mapping per transform. Lifting this needs binary-format, core and compiler changes, pencilled in for v20.
  • One loose end: <import path="47/…"> is accepted and treated as 46, while conformsTo="47" is rejected.

Where KMX+ fits

KMX+ is the binary form Keyman compiles an LDML keyboard into. It is not a separate file type: it is a block inside an ordinary .kmx, marked by a header flag. The studio exports LDML source, and Keyman's LDML compiler turns that into KMX+. Nothing else in Keyman writes KMX+; KMN keyboards still compile to classic .kmx.

KMX+ file versionKeyman's axis
  • v17 (0x1100) is what every Keyman compiler writes today.
  • The unmerged web-core branch adds KMX+ v19, with a version on every section, behind a compiler option.
  • Core refuses a file newer than it supports; there is no fallback.
  • Independent of conformsTo: nothing maps one to the other. The studio never writes KMX+, so it doesn't choose this.
KMX+ is where Keyman's touch plans converge web-core (Keyman 20): the browser engine, and so Android and iOS, will load .kmx files through Core compiled to WASM. That brings the hardware half of LDML keyboards to mobile. Reading the touch tables (layr, disp, key gestures) is still a TODO there (#15290, #13429, #8093). #12620 (open, Keyman 20): Keyman plans to convert a KMN keyboard's .kvks and .keyman-touch-layout into LDML and compile them into KMX+ tables inside the .kmx, giving one file for every platform. That is the same touch-to-LDML conversion the studio's export performs, so spec-perfect touch LDML is on Keyman's own roadmap.

Touch is the big gap, but it is Keyman's gap

The same touch markup is valid in 46 and 49. What is missing is Keyman's ability to run it, at every stage after compilation:

Valid in 46 and 49

Compiles it

Stored in the KMX+ layr, keys and list sections of the .kmx.

Keyman desktop (Core)
Ignores it

Core reads only the KMX+ key map, transforms and variables. layr and the gesture data are validated, then never used.

Rejects the file

The loader throws ".kmx files are not currently supported". Android and iOS run on KeymanWeb, so neither half loads.

The "no key input" gap is touch layer state, not text

KMN cannot rewrite text without a keystroke either:

  • Context-only groups run only when a keystroke rule hands off to them with use(). LDML covers that with chained transformGroups.
  • begin NewContext and begin PostKeystroke must use readonly groups, which cannot emit text.

In the corpus, 50 of 1,036 keyboards use them. All 97 of those groups are readonly, and all of them are used for touch auto-layer switching.

What this means for the studio's version picker

The two export profiles differ in three tokens of output. The touch half is spec-perfect and identical in both, so a 46 export loses nothing on touch.

Profile 46Default · Keyman compiles it
<keyboard3 xmlns="https://schemas.unicode.org/cldr/46/keyboard3"
           locale="ibn" conformsTo="46">
  <info name="Ibọnọ Chwerty" author="…"/>
  <!-- attribution: carried in this comment
       and in the .kps -->
  • Builds in Keyman 19 and 20-alpha today.
  • Desktop runs the hardware half. The touch half compiles and waits for Keyman 20.
  • Attribution travels in the header comment and the package.
Profile 49TR35-only · awaiting Keyman
<keyboard3 xmlns="…/cldr/49/keyboard3"
           locale="ibn" conformsTo="49">
  <info name="Ibọnọ Chwerty" author="…"
        attribution="…"/>
  • The newest valid CLDR output, for other LDML implementations and for the future.
  • Every Keyman tool fails to build it until Keyman ships a 47+ schema.
  • Must not emit $[N:set] with N > 1: the CLDR 49 grammar allows only $[1:set], so set mappings outside group 1 are expanded, as in profile 46.
Recommendation: Keep 46 as the default. Because the touch half is identical, "spec-perfect touch, ready for Keyman's pipeline" is already met by profile 46. Profile 49 only adds attribution metadata, at the cost of Keyman refusing the file. The version profiles stay useful because the next CLDR version may change more than this one did. The studio exports LDML, not KMX+, so the KMX+ version stays Keyman's concern. For a build check, the studio could probably run Keyman's LDML compiler in the browser, which has no file-system dependencies, if it bundles the compiler's WASM and the CLDR import files. That is untested.
